# ミゴロン予報の精度レビュー計画

ミゴロンの指数（星空・雲海・富士山・花畑）が当たっているかを継続して見て、2週間ごとを目安に計算式を見直すための手順書。

## 1. 何を測っているか

| 指標 | 意味 | 見方 |
|---|---|---|
| 的中率 | 「指数60以上＝見られる」の予測と結果が一致した割合 | 高いほど良い |
| Brierスコア | `(指数/100 − 結果(0か1))²` の平均 | 0に近いほど良い。常に50%と答えると0.25 |
| 偏り | 予測−結果の平均（点） | +なら高く出し過ぎ、−なら低く出し過ぎ |
| 信頼度の表 | 出した指数の帯ごとに、結果が良かった割合 | 80〜95%の帯が8割以上なら指数は信頼できる |
| ライブカメラ判定との一致 | 富士山：公開ライブカメラの画像をAIで判定した「実際に見えたか」と予測の一致率 | これだけが本当の正解 |

**注意**: 的中率・Brier・偏りの「結果」は、Open-Meteoの過去値（予報モデルの解析値）を同じ式に入れ直したもので、実際に見えたかどうかではない。前日の予報が当日どれだけ変わったかを測っている。計算式そのものが現実と合っているかは、ライブカメラ判定（いまは富士山のみ）でしか分からない。

花畑は当日朝の予報と当日の値を比べる形になり、ほぼ必ず一致する。判定の対象から外している。

## 2. 現在地（2026-11-21時点、10/25〜の28日間）

| 種別 | 的中率 | Brier | ズレ平均 | 件数 |
|---|---|---|---|---|
| 星空 | 94.6% | 0.066 | 5.2点 | 130 |
| 雲海 | 90.7% | 0.121 | 6.3点 | 75 |
| 富士山 | 86.7% | 0.121 | 10.4点 | 75 |
| 全体（花畑含む） | 92.6% | 0.097 | 5.8点 | 336 |

最初の1週間（10/26〜11/1）は富士山が66.7%だったが、15件だけの数字だった。14日ぶん（富士山・雲海は42件）でも、偶然で±5ポイント程度は動く。

## 3. 合格ラインと目標

合格ラインは「これを割ったら原因を調べる」線。`src/lib/prediction-log.js` の `TARGETS` に入っている。目標は次に目指す値。

| 種別 | 合格ライン（的中率 / Brier / 偏り） | 目標（的中率） | 考え方 |
|---|---|---|---|
| 星空 | 90% / 0.12以下 / ±8点 | 95%を維持 | すでに高い。維持が目標 |
| 雲海 | 85% / 0.15以下 / ±8点 | 92% | 風と湿度の予報が当日に動く分が外れの主因 |
| 富士山 | 85% / 0.15以下 / ±8点 | 90% | ズレが10点と大きい。視程の扱いと、晴れた日に95%へ張り付く点が改善余地 |
| ライブカメラ判定との一致（富士山） | 75%（14日で5件以上あれば判定） | 80% | 現実の天気は予報モデルより外れやすいので、的中率より低く置く |

前日予報どうしの比較である以上、的中率は95%前後が上限とみている。それ以上は式の改善ではなく、指数が60から離れた日が多いかどうか（季節）で決まる。

## 4. レビューの進め方（2週間ごと）

1. `/admin` の「ミゴロン予報のレビュー」を開く（同じ内容のJSONは `/api/verify-predictions?review=1&key=<CRON_SECRET>`）。
2. 種別ごとの判定を見る。
   - **合格**: 何もしない。
   - **様子見**: 基準を1つ外した。次回も続くかを見る。
   - **要見直し**: 的中率が合格ラインより10ポイント以上低い、偏りが±16点を超える、基準を2つ以上外した、ライブカメラ判定との一致が75%未満、のどれか。下の3へ進む。
   - **データ不足**: 14日で15件未満。投稿が止まっていないか `/admin` の稼働状況を確認する。
3. 要見直しのときは「外れた予測」の一覧で、外れ方の共通点を探す。
   - 「高く出し過ぎ」が多い → 減点が足りない要素を探す（例: 視程が低いのに高得点）。
   - 「低く出し過ぎ」が多い → 減点が強すぎる要素を探す（例: 1時間の雨コードで−40）。
   - 特定のスポットだけ外れる → `spots.json` の座標、またはその地点の予報の癖を疑う。
4. `src/app/api/_lib/migoron-scoring.js` の係数を直す。直す前後で `?dry=1` の結果を比べ、Jakeに見せてからマージする。
5. 変更した日と内容を下の「変更履歴」に書く。次のレビューで、変更前後の14日を比べる。

**1回のレビューで式を変えるのは1種別・1要素まで。** 複数を同時に変えると、どれが効いたか分からなくなる。

## 5. 自動の記録と判定（手作業なし）

| 時刻(JST) | 処理 | 記録先 |
|---|---|---|
| 毎朝 8:20 | 富士山のライブカメラ判定（`/api/check-fuji-camera`） | 予測ログ（Redis）の `actual` |
| 毎朝 9:00 | GitHub Actionsが予測・答え合わせ・カメラ判定をCSVに追記 | `migoron-monitoring` ブランチの `predictions.csv` |
| 毎晩 22:40 | 答え合わせ（`/api/verify-predictions`） | 予測ログ（Redis）の `verified` |
| 毎月1日・15日 9:00 | 上の処理に加えてレビューをMarkdownで保存 | 同ブランチの `reviews/YYYY-MM-DD.md`、`latest-review.md` |
| 毎月1日・15日 9:52 | Claude Codeの定期実行が `latest-review.md` を読み、判定と修正案を報告 | このリポジトリの作業セッション |

ライブカメラは次の2台。画像は判定に使うだけで保存・再配布しない。

| カメラ | 画像 | 判定するスポット |
|---|---|---|
| 静岡県「ライブカメラ富士山ビュー」富士宮 | 毎朝8時の写真（640×480） | 田貫湖 |

注意: 富士山指数の「ベスト」は5〜7時だが、冬は日の出が6時半過ぎで暗いため、カメラは8時台の画像で判定している。早朝だけ晴れて8時には雲が出た日は「外れ」に数えられる。夜間・故障などで判定できない日（`unusable`）は記録しない。

## 6. 検討中の改善案

- 富士山: 視程の減点を段階的にする（現状は10km未満で一律−20点）。
- 富士山: 晴れた日に全地点が上限95%へ張り付くのを緩める。
- 雲海: 風速が強い地点（7m/s以上）の扱い。

いずれも、レビューで「要見直し」が出るか、ライブカメラ判定で外れが続いたときに着手する。
