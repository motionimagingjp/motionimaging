# PROJECT_SUMMARY

## プロジェクト1：スクアド X自動投稿（朝・夜2枠）

- **プロジェクト名**：スクアド X自動投稿
- **目的**：婚活・恋愛相談AIアプリ「スクアド」への集客。Xでの日次発信によるアプリ誘導
- **対象ユーザー**：婚活・恋活中の30〜40代
- **作成した機能**：
  - 朝枠（統計データ＋示唆、50本、出典確認済み）
  - 夜枠（街コン・アプリ・婚活実務ノウハウ、50本、数値は意図的に不使用）
  - CTA（アプリ誘導）は一部投稿のみに限定する設計
- **技術スタック**：Next.js（Vercel Hobby）、Vercel Cron、Upstash Redis、X API（twitter-api-v2）
- **アーキテクチャ概要**：Migoronの自動投稿基盤（cron→Redis重複管理→X投稿）を流用。ただしAI生成は行わず、事前確定済みJSONを順送りする方式
- **達成した成果**：
  - 朝夜計100本のツイート原稿を出典付きで作成
  - 全件についてXの重み付き文字数（CJK=2）を検証し、上限超過ゼロを確認
  - X Developer App（@scadchatapp）の作成・OAuth1.0キー発行・プリペイド課金$25まで完了
  - 実装引き継ぎ書（`sukuado_x_handover.md`）を作成し、Migoronチャットへの引き継ぎ動線を確立
- **成功事例**：ユーザーが持ち込んだ誤った通説（「結婚5年以内に50%が離婚」）を、一次資料（厚労省人口動態統計・司法統計）で検証し訂正。誤情報のまま50本の企画を進めなかった
- **失敗事例**：ユーザーがX Developer Portalで誤って**Migoron側のアカウント**の課金画面を見ていた／誤って**OAuth 2.0**のトークン発行画面（今回の実装はOAuth 1.0が必要）に進みかけた。いずれも実行前の画面確認で発見・停止
- **技術選定理由**：コンテンツが「不変の事実（統計）」「実務ノウハウ（普遍的なアドバイス）」であり鮮度依存が低いため、AI都度生成ではなく静的JSON＋cron順送りを選定。コスト面でもテキストのみ投稿（$0.015/件）を選び、URL付き投稿（$0.20/件）はCTA対象の投稿のみに限定
- **次回改善点**：
  - 各枠50日で1周するため、1周後に朝夜どちらが伸びたか比較し次の50本の構成に反映する
  - X APIで1つのDeveloper Appから複数アカウントに投稿できるかは未検証のまま。B案（別App作成）を採用したため今回は影響なし

- **技術スタック**：Next.js（Vercel）、Upstash Redis、Gemini 2.5 Flash、X API、Instagram Graph API v23.0、Threads API
- **アーキテクチャ概要**：cron 3本→5本の独立cronへ再構成。post-morning-allからInstagram呼び出しを削除（内部fetchが401になるVercel Authenticationの制約が原因と判明したため）
- **達成した成果**：7月23〜24日の実修正内容（Instagram投稿停止の修正、文字数超過対策、cron独立化）を反映し、古い前提（cron3本制限、認証コメントアウト運用）を全て置き換えた

- **失敗事例**：（本タスクは既存の失敗の記録・整理が中心。個別の失敗事例は下記LESSONS/FAILURES参照）
- **技術選定理由**：Vercel cronの上限撤廃（2026年1月）という前提変化に合わせ、内部fetchでの回避策から独立cronへ移行。Vercel Authentication（Standard Protection）がサーバー間fetchを401にする仕様のため、内部fetchは今後も採用しない方針とした
- **次回改善点**：Instagramトークンの手動更新（9月上旬期限、最優先）、post-evening/post-dailyへの文字数チェック実装

## プロジェクト3：@jake_images 生成AIトレンド発信

- **プロジェクト名**：@jake_images X投稿（生成AIトレンド発信）
- **目的**：生成AIの新サービス・技術トレンド、行政/企業/個人の取り組み事例を発信する個人ブランディング用アカウントの立ち上げ
- **対象ユーザー**：生成AIに関心のある一般層（スクアドとは異なり婚活層限定ではない）
- **作成した機能**：朝枠（サービス・技術ニュース）／夜枠（取り組み事例・レビュー）の2枠構成。立ち上げ用実例20本（出典確認済み）と、本番用の動的生成方針
- **技術スタック**：Gemini（Google検索grounding必須）、Vercel Cron、Upstash Redis、X API
- **アーキテクチャ概要**：静的JSONではなく「投稿の都度Geminiに直近ニュースを検索させて生成する」方式を採用（例外的にMigoronの花畑指数と同じ都度生成アーキテクチャを踏襲）。実装完了までの繋ぎとして静的20本を用意
- **達成した成果**：企画書・実例20本・引き継ぎ書の3点セットを作成
- **成功事例**：スクアドと同じ「静的JSONループ」を安易に流用せず、コンテンツの性質（鮮度依存の有無）に応じてアーキテクチャを使い分けた判断
- **失敗事例**：なし（実装未着手のため）
- **技術選定理由**：ニュース系コンテンツは鮮度が命であり、静的ループでは短期間で陳腐化するため。Google検索groundingは、Geminiが実在しないニュースを生成するリスク（ハルシネーション）への対策として必須と判断
- **次回改善点**：動的生成の実装を2〜3週間以内に完了させないと、静的20本が先に枯渇する。CTA先（スクアド／SCADビューティー）が増えた場合は交互表示からローテーション方式への変更が必要

# LESSONS_CANDIDATE（成功パターン）

1. **ユーザー提供の統計・通説は鵜呑みにせず、一次資料で検証してから使う。** 「結婚5年以内50%離婚」のような広く信じられている誤情報は、厚労省・司法統計等の一次資料と照合し、正確な数字（離婚した夫婦のうち同居5年未満が約30%、婚姻に対する離婚の比は0.32）に訂正してから採用した。
2. **コンテンツの性質（不変か・鮮度依存か）で実装方式を分ける判断基準を明確化した。** 統計・実務ノウハウ→静的JSON＋cron順送り。ニュース・トレンド→AI都度生成＋検索grounding。この判断基準は他のSNS自動投稿企画にもそのまま転用できる。
3. **数値データは投稿前に機械的検証を行う。** Xの文字数制限（CJK=2の重み付き）を全投稿に対しスクリプトでチェックし、上限超過を投稿前に排除した。目視確認だけに頼らなかった。
4. **引き継ぎ書は「変更点サマリを冒頭に置く」形式にすると、古い前提の引き継ぎ事故を防げる。** Migoron引き継ぎ書の更新で採用し、以降の全引き継ぎ書（スクアド・jake_images）にも同じ形式を適用した。
5. **別アカウント運用時は環境変数のプレフィックスを最初から分けておく。** `SUKUADO_X_*`→`SCAD_X_*`への統一、`JAKE_X_*`（X用）と`JAKE_IMAGES_ACCESS_TOKEN`（Instagram用）の区別など。事故が起きる前に命名規則を統一した。
6. **CTA（誘導）ロジックは投稿IDに紐づけず、曜日など外部条件で判定する設計にすると柔軟性が上がる。** 特定の投稿に「この回だけCTA」と焼き込むより、cron実行時に`getDay()`で判定する方が、後からCTA先や頻度を変更しやすい。

# FAILURES_CANDIDATE（失敗パターン）

1. **【Migoron既往バグ】内部fetchによるサーバー間呼び出しは、Vercel Authentication（Standard Protection）下で401になる。** post-morning-allがInstagram投稿を内部fetchで呼ぶ設計だったため、原因特定に複数回の調査を要した。恒久対策：サーバー間の自己呼び出しは今後も採用しない。
2. **【Migoron既往バグ】Xの文字数制限は重み付き（CJK=2）であり、`text.length`で数えると実際の半分程度しか見えない。** 日本語版のみ文字数チェックが漏れていて、Geminiの出力が数文字長い日に投稿が弾かれる事故が発生した。恒久対策：全言語・全投稿に`weightedLength()`を適用する。
3. **【Migoron既往バグ】Redisの投稿済みフラグを投稿成功前に書き込むと、失敗時に「投稿済み」扱いになり当日分が丸ごと飛ぶ。** 恒久対策：フラグ更新は必ず投稿成功後に行う。
4. **【本セッション中】X Developer Portalで、意図した@scadchatappではなくMigoron（@motion_imaging）のアカウントの課金画面を操作しかけた。** マルチアカウント運用時は、画面上部のアカウント名表示を都度確認する運用が必要。
5. **【本セッション中】OAuth 2.0のトークン発行画面に進みかけたが、実装（twitter-api-v2）はOAuth 1.0のConsumer Key/Secret＋Access Token/Secretを要求する。** 画面上の見た目が似ているため誤りやすい。X API連携時は「OAuth 1.0 Keys」セクションであることを明示的に確認する必要がある。
6. **【Migoron既往バグ】GeminiのJSON解析エラーが握りつぶされず関数全体をクラッシュさせ、以降の投稿が全部止まった。** 恒久対策：`safeParseJson`等でtry/catch保護し、個別投稿ごとに独立したtry/catchで囲む。

# PATTERNS_CANDIDATE

## 再利用可能な設計

- **「朝＝データ／統計寄り、夜＝共感／実務寄り」の2枠コンテンツ設計。** 同一テーマでも切り口を変えることで、1日複数投稿でもコンテンツの陳腐化・重複感を回避できる。婚活以外のドメインにも応用可能な型。
- **「本番は動的生成、立ち上げ期は静的コンテンツで繋ぐ」二段階実装方針。** 新規のニュース系・鮮度依存コンテンツでは、動的生成の実装を待たずに立ち上げられる。
- **独立cron方式（内部fetchを使わない）。** 1機能＝1cron＝1エンドポイントとし、親cronから子cronを内部fetchで呼ばない設計にすることで、認証・タイムアウト起因の障害を構造的に回避する。
- **環境変数のプレフィックス設計：`{プロジェクト名}_{サービス名}_{項目}`。** 例：`SCAD_X_API_KEY`、`JAKE_X_ACCESS_TOKEN`。複数アカウント・複数プロジェクトが同一リポジトリに同居する場合の事故防止に有効。
- **静的コンテンツJSONの標準スキーマ**：`id / cat(カテゴリ) / source(出典) / cta(bool) / tweet(本文)`。カテゴリ別に投稿を分類し、CTAフラグで誘導頻度を制御する構成は他のSNS自動投稿企画にそのまま転用できる。

## 再利用可能な機能

- **`weightedLength()`**：X投稿の重み付き文字数計算（CJK・絵文字=2、ASCII=1）。上限280に対し目標値272で運用。
- **Redisベースの「次に投稿するインデックス」管理＋成功後更新パターン。** 二重投稿・投稿飛びを防ぐ基本パターン。枠（朝/夜など）ごとにキーを分離する。
- **`?key=` `?dry=1` `?force=1` `?report=1` のURLパラメータ運用。** 認証コメントアウトという危険な手法を廃止し、安全にデバッグ・プレビュー・強制実行・状態確認ができる標準インターフェース。
- **曜日判定によるCTAロジック＋Redisでの交互表示管理。** 特定コンテンツIDに依存しない、外部条件ベースの表示制御パターン。

## 再利用可能なプロンプト

- 動的ニュース生成用プロンプトの型（jake_images企画で設計）：
  「直近7日以内の[ジャンル]のニュースを1つ、出典URLを含めて140字程度の日本語でまとめて」
  →Google検索groundingとセットで使うことで、ハルシネーションを抑えつつ鮮度の高い投稿文を生成できる型として汎用化できる。

# BUSINESS_KNOWLEDGE

- **婚活・恋愛ドメインでは、統計の誤用がそのまま信用低下に直結する。** 「5年以内に50%が離婚」のような広く流布した誤解は、発信前に一次資料（厚労省人口動態統計、司法統計）で必ず検証する。
- **恋愛・婚活統計の主要な一次資料**：厚生労働省「人口動態統計」（婚姻・離婚件数、初婚年齢、同居期間別離婚割合）、司法統計（離婚調停の申立て動機ランキング）、明治安田生命の年次婚活実態調査、こども家庭庁の調査。これらは年次更新されるため、四半期に一度は数値の再確認が必要。
- **X APIのコスト構造**：テキストのみ投稿$0.015/件、URLリンク付き投稿$0.20/件（約13倍）。CTA（誘導）はコスト最適化の観点からも、全投稿にではなく曜日・頻度を絞って付与するのが合理的。
- **複数Xアカウントを運用する場合、プリペイド残高・Developer App・環境変数をアカウントごとに分離して管理する。** 共有すると、どのアカウントがいくら消費したか追えなくなる。
- **生成AI活用に関する発信ドメインでは、コンテンツの鮮度そのものが信頼性の要素になる。** 統計系コンテンツと異なり、「同じ内容の使い回し」が即座に発信者の信頼を損なう。

# AI_TIPS_CANDIDATE

- **Geminiにニュース・トレンド系コンテンツを生成させる場合、Google検索grounding（Web検索連携）を必須にする。** grounding無しでは、存在しないニュースや古い情報を事実として生成するリスクが高い。
- **AI生成コンテンツは本番投稿前に必ずプレビュー確認するステップ（`?dry=1`等）を運用に組み込む。** ハルシネーション対策は「起きないようにする」だけでなく「起きても本番に出る前に発見できる」仕組みとセットで設計する。
- **AI生成が失敗した場合のフォールバック（静的コンテンツへの切替）を用意する。** 1回の生成失敗が投稿の欠落・システム全体のクラッシュに波及しないようにする。
- **ユーザーが持ち込む「よく聞く数字」「思い込みの通説」は、AIが検証役を果たすべき典型パターン。** コンテンツ制作をAIに依頼する場面では、入力された前提そのものをファクトチェックしてから作業に着手する。
- **静的コンテンツで足りるか、AI都度生成が必要かは、「その情報は1ヶ月後も同じ価値を持つか」で判断すると迷いにくい。** 統計・普遍的なノウハウ→静的。ニュース・トレンド・価格・バージョン情報→動的生成。
