# PROJECT_SUMMARY

- **プロジェクト名**：スクアド（前身：DECODE／DECODE v2）
- **目的**：LINE等のやり取りのスクリーンショットを解析し、相手の心理状態・関係性に合わせた返信内容とタイミングをAIがアドバイスするコミュニケーション支援アプリ。将来的にはビジネス（営業プロセス管理）、教育（教師生徒間）、友人関係への応用も視野。
- **対象ユーザー**：婚活・恋愛中の個人ユーザー
- **作成した機能**：
  - ストリーミングチャット（Gemini `streamGenerateContent`）
  - ゲスト利用（LocalStorage）とログイン利用（Supabase同期）の両立
  - 3人の恋愛アドバイザー人格切替（男性・女性・ジェイ本人）
  - 4部構成の分析レポート（読み取れること／返信案／理由／送るタイミング）
  - 洋服・レストランへの一時的なアドバイザー切替と自動復帰
  - 相手（パートナー）ごとの継続管理・複数相手の切替UI
  - 表1に基づく熱量スコアリング（接触回数・文字数比率・返信時間・属性補正・リスク制御）
  - 匿名化統計基盤（学習用データを個人データから分離）
  - 同意画面（スクロール必須型）とプライバシーポリシー3案
- **技術スタック**：Next.js 16.2.12（App Router）／TypeScript／Tailwind CSS v4／Supabase（Auth・DB・RLS）／Gemini 2.5 Flash／Vercel
- **アーキテクチャ概要**：
  ```
  ブラウザ → Next.js API Route（GEMINI_API_KEYを隠蔽） → Gemini API
                    ＋
  Supabase（個人用：認証・相手・履歴・RLSで本人のみ読める）
  Supabase（学習用：別プロジェクト・匿名化データのみ・user_id等を持たない）
  ```
- **達成した成果**：
  - DECODE v2のコード一式完成・ビルド確認済み（型エラー0、npm audit 0件）
  - スクアド全体設計書・DBスキーマv0.2完成
  - プライバシーポリシー3案（Word化）作成
  - 弁理士への特許相談を実施済み（2026年5月）
- **成功事例**：LESSONS_CANDIDATE参照
- **失敗事例**：FAILURES_CANDIDATE参照
- **技術選定理由**：
  - Next.js：1ファイル1,100行だった旧HTML版の保守性問題を解消するため
  - Supabase：認証・DB・RLSがワンストップで揃い、非エンジニアでも運用しやすいため
  - Gemini 2.5 Flash：既存実装からの継続、ストリーミング対応
  - DBでのプロンプト・パラメータ管理：コードを書かない運用スタイルのため、機能追加をDB編集で完結させる目的
- **次回改善点**：NEXT_STEPS参照

# LESSONS_CANDIDATE

**成功パターン**

- ストリーミング応答の導入により、旧版の「考え中で待たせる」体験から体感速度が大きく改善した。
- ゲストモード（LocalStorage）とログイン（Supabase）を両立させたことで、離脱率を上げずに端末間同期という価値を提供できた。
- プロンプトに「統計は傾向であり断定ではない」という注意書きを明示することで、外れた場合の信頼喪失リスクを事前に設計で潰した。
- 「個人の実データ ＞ セグメント統計 ＞ 全体平均」という優先順位をプロンプト内に明記する設計により、データが少ない初期段階でも破綻しないアドバイスロジックを実現。
- アドバイザーの人格・プロンプト・パラメータをコードでなくDBで管理する設計にしたことで、開発者（Claude）を介さずに運用改善できる余地を作った。
- パラメータ更新履歴（`metric_update_logs`）を残す設計にしたことで、特許戦略上の「アルゴリズムの自動更新」の実施証跡が自然に残る。
- 同意画面を「スクロール必須＋同意ボタン」形式にすることで、チェックボックスなしでも法的に説明力のある同意取得ができる設計にできた。
- データ活用のフェーズを「貯めるだけ（今）→使う（将来）」と明確に分離したことで、機能不足を無理に埋めようとせず段階的に開発を進められる状態にした。
- 匿名化データ（`anon_patterns`）をユーザー退会後も保持し続ける設計にすることで、退会があってもDB資産が目減りしない構造にした。

# FAILURES_CANDIDATE

**失敗・要注意パターン**

- 「本文を生成AIの学習・解析パイプラインに渡さない」という特許戦略の主張と、実装（Supabaseへの会話履歴保存）が矛盾していたことに、レビューで初めて気づいた。特許戦略とプロダクト実装のすり合わせを先に済ませておくべきだった。
- 過去、iOS版の開発をFlutterFlowで進めていたが、無料プランのState Management制限と数値入力欄への手入力ができない問題で頓挫した経緯がある（→ iOS版は当面見送り、Web優先の判断につながった）。
- Geminiのモデル名変更に過去4回対応させられた経緯があり、モデル名を決め打ちしない・エラー時に一覧取得する運用ルールが必要だった。
- LINEのスクリーンショットは送受信のタイムスタンプが省略されることが多く、熱量スコアの中核変数である「返信時間（T）」「送信時間帯」が技術的に取得困難なケースが多いことが判明。設計時点で全項目が揃う前提にしていたら破綻していた。
- セグメント統計（職業×年代の20区分×サンプル30件＝計600件）は、実際のユーザー数を考えると当面（1年でも）到達しない可能性が高いと判明。過度な期待を早期に修正できた。
- 特許出願が完了する前にアプリを一般公開すると、新規性を喪失し権利化できなくなるリスクがある。プロダクト開発と特許相談のスケジュールを個別に管理していなかった場合に発生しうる重大なリスクだった。

# PATTERNS_CANDIDATE

**再利用可能な設計**

- 個人データ用DBと学習用（匿名化）DBを**別のSupabaseプロジェクトに分離**する設計。`user_id`・`partner_id`・呼び名を学習用データに一切持たせないことで、プライバシーと再利用性を両立。
- アドバイザーの人格・システムプロンプト・トリガーキーワード・持続ターン数をテーブル化（`advisors`）し、コード変更なしで追加・調整可能にする設計。
- ロジックのパラメータ（表1のような変数群）をコード直書きではなく`metric_definitions`テーブル＋JSONで管理し、更新履歴（`metric_update_logs`）を残す設計。
- データ充足度に応じた**段階的フォールバック**（個人実データ→セグメント統計→年代のみ統計→一般論）というロジック。データが少ない立ち上げ期でも破綻しない。
- キーワード検知による**一時サブモード切替＋条件付き自動復帰**（トリガー語検知→確認バー表示→本人の選択→数ターンで自動的にホームに戻る）という会話フロー設計。
- RLS（Row Level Security）で「本人の行しか読めない」をDB側で強制する設計。
- 同意記録をバージョン付きで残す`user_consents`テーブルのパターン（ポリシー改定時に再同意を求められる）。

**再利用可能な機能**

- Gemini streamGenerateContentによるストリーミングチャットUI
- ゲスト（LocalStorage）／ログイン（Supabase）のハイブリッド履歴管理
- スクリーンショットからの構造化メタデータ抽出（JSON形式で本文を持たずに数値だけ取り出す仕組み）
- 相手（対象者）ごとの継続管理と、成果（デート成立等）の自動フォローアップ質問
- サブジャンル（洋服・レストラン等）へのアドバイザー切替UIとその自動復帰ロジック

**再利用可能なプロンプト**

- 統計情報をAIに渡す際の注意書きテンプレート：
  「これは一般的な傾向であり、目の前の相手が必ずそうとは限りません。個人の実データがあればそちらを優先してください。サンプル数が閾値未満の場合は統計に触れないでください。」
- 匿名化要約プロンプト：「人名は『相手』『Aさん』、地名・企業名は一般名詞に置換し、識別子は完全に除去したうえで3行以内に要約する」
- アドバイザー用プロンプトの5ブロック構成テンプレート：
  ①人格 → ②相手プロフィール → ③個人の実データ（最優先） → ④セグメント統計（補助） → ⑤今回の相談内容

# AI_TIPS_CANDIDATE

**AI活用ノウハウ**

- コードは部分diffではなくファイル全体で受け取る運用にすることで、「削除→新規作成」で貼り付け事故を防止できる。
- AIモデル（Gemini等）のモデル名はコード内で決め打ちにせず、エラー発生時にまず利用可能なモデル一覧を取得して確認する運用が安全。
- Supabaseの`cookies()`はNext.js 15以降非同期のため、`await`を忘れると型エラーになる（古い記事のコードをそのまま貼ると失敗しやすい）。
- middlewareの`supabase.auth.getUser()`は一見不要に見えてもセッション更新のために必須。安易に削除するとログインが切れる。
- AIへの指示文で「個人の実データを優先し、統計は補助的に使う」という優先順位を明示すると、データが薄い状況でもAIの回答が破綻しにくい。
- 「サンプル数が閾値未満の場合は機能させない」というガード条件をパラメータ化しておくと、初期データ不足時に誤った統計的主張をAIにさせずに済む。
- 機密性の高い議事録・特許relatedの文書を貼る際は、事前にAIプロダクトのプライバシー設定（学習利用のオプトアウト状態）を確認する運用が安全。
- 大きな設計変更の前に「今のままだと矛盾する点」を洗い出すレビューを挟むと、後戻りの大きい問題（法務・特許系）を早期に発見できる。
