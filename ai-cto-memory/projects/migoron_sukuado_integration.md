# PROJECT_SUMMARY

- **プロジェクト名**：Migoron SNS自動投稿システム／スクアド X自動投稿（同一Vercelリポジトリ内の2プロジェクト）
- **目的**：
  - Migoron：風景・ポートレート写真家ブランドのSNS運用を完全自動化し、手作業ゼロで毎日の投稿を継続する
  - スクアド：新規リリースした恋愛・婚活AI相談アプリ「スクアド」の集客をX上で自動化する
- **対象ユーザー**：
  - Migoron：西村本人（運用者）、フォロワーは風景・ポートレート写真に関心のある層
  - スクアド：婚活・恋活中の30〜40代（Xアカウント @scadchatapp のフォロワー想定）
- **作成した機能**：
  - Instagram自動投稿（@motion.imaging、@jake_images_）：Gemini Visionでテーマ判定、キャプション自動生成、Threads同時投稿
  - X自動投稿（Migoron @motion_imaging）：花畑指数・お出かけ開運指数・星空指数・雲海/富士山指数を毎日生成
  - X自動投稿（スクアド @scadchatapp）：朝（統計データ50本）・夜（実務アドバイス50本）・宣伝（固定3パターン）の3枠
  - 全エンドポイント共通のデバッグ用クエリパラメータ（`?key=` `?dry=1` `?force=1` `?report=1`）
- **技術スタック**：Next.js（App Router）+ Vercel（Hobbyプラン、Fluid Compute有効）、GitHub（コード・画像ホスティング）、Upstash Redis（状態管理・重複防止）、Gemini 2.5 Flash（キャプション・指数生成）、Open-Meteo API（天気）、X API（twitter-api-v2、プリペイド課金）、Instagram Graph API（v23.0、Meta app経由）
- **アーキテクチャ概要**：
  - Vercel Cronで日次実行（現在8本：Migoron5本＋スクアド3本）
  - 各外部副作用（Instagram投稿、X投稿）は**独立したcronエンドポイント**として分離し、内部fetchによるcron間の呼び出しは行わない
  - Redisで「本日投稿済みフラグ」「ローテーションindex」「周回数」「直近実行レポート」を管理
  - スクアドは共通ロジック（`runSukuado`）を`slot`パラメータで朝/夜/宣伝に出し分ける設計
- **達成した成果**：
  - Instagram投稿停止の根本原因（内部fetchの構造的欠陥＋Vercel Authenticationによる保護）を特定し解消
  - X投稿の「文字数超過による抜け」を、Xの実際の重み付きカウント方式に合わせて解消
  - スクアドの朝夜2枠＋宣伝1枠、計3エンドポイントを新規構築し実投稿確認まで完了
  - Vercel Hobbyプランのcron本数制限撤廃（2026年1月）という環境変化を発見し、アーキテクチャを再設計
- **成功事例**：後述 LESSONS_CANDIDATE 参照

- **技術選定理由**：後述 各セクション参照

# LESSONS_CANDIDATE（成功パターン）

## 1. デバッグ用クエリパラメータの標準装備
`?key=CRON_SECRET`（認証コメントアウト不要）、`?dry=1`（投稿せず本文・文字数を確認）、`?force=1`（重複チェック無視）、`?report=1`（Redisに保存した前回実行結果を表示）の4点セットを全エンドポイントに実装。Vercel Hobbyプランは実行ログが見にくいため、**アプリ自身に観測可能性を持たせる**ことで有料ログなしで運用できた。

## 2. 消去法によるバグの切り分け
Instagram投稿が止まった際、「トークン」「環境変数」「画像URL」を個別に直接叩いて正常性を確認し、原因を「呼び出し経路（内部fetch）」に絞り込んだ。表面的な仮説（実行時間不足）で満足せず、実際のログ（Host、Firewall、Execution Duration）を見て、より根本的な原因（Vercel Authenticationによる内部URL保護）に到達した。

## 3. 環境の前提を都度疑う
「Vercel Hobbyはcron3本まで」という2026年7月時点の制約は、2026年1月の仕様変更で撤廃済みだった。過去の制約を前提にした設計（内部fetchで1本のcronに集約）が、制約解消後は不要な複雑さとリスクの温床になっていた。**制約を回避するための設計は、制約が消えたら見直す対象になる**。

## 4. 外部APIの「見えない仕様」を実測で検証
Xの280字制限が実際には「重み付き」（CJK・絵文字は2、URLは23固定）であることをドキュメントベースで確認し、`weightedLength()`として実装。既存コードの`text.length`ベースの文字数計算が、この仕様とズレていたことが「投稿が時々抜ける」不具合の真因だった。

## 5. カテゴリ分散のための決定的アルゴリズム
スクアドの投稿データがカテゴリごとに固まっていた（同カテゴリ10連続）問題を、ラウンドロビン方式の`interleaveByCategory()`で解消。**乱数ではなく決定的な並べ替え**にすることで、`?dry=1`で見た順序と実際の投稿順序が完全一致し、事前確認の信頼性を保った。

## 6. 共通ロジックの一元化とslot切り替え
朝・夜・宣伝の3つの投稿枠を、個別実装ではなく`runSukuado(request, slotName)`という1つの関数にまとめ、Redisキー・データソースだけを`SLOTS`定義で出し分けた。新しい枠（宣伝）を追加する際、コアロジックの変更は数行で済んだ。

## 7. Redisフラグは「成功後」に更新する原則の徹底
投稿失敗時に重複防止フラグやローテーションindexが進んでしまうと、その日の投稿が失われた上に翌日以降もズレる。「フラグ更新は投稿成功を確認した後」という原則を全エンドポイントで統一した。

# FAILURES_CANDIDATE（失敗パターン）

## 1. 「直接叩けば成功」を早期に「解決」と誤認した
post-instagramを直接実行して成功したことをもって「Instagram投稿問題は解決」と判断したが、実際にはpost-morning-all経由での成功を一度も確認していなかった。翌朝も投稿されず、検証の穴が露呈。**修正の確認は、実際に使われる経路（cron経由）で行う必要がある**。

## 2. 一度目の原因特定が不十分だった
最初はInstagram呼び出しの「120秒AbortControllerタイムアウト」を主因と断定して修正したが、翌朝も失敗。実際の根本原因はVercel Authentication（Standard Protection）による内部fetchの401エラーだった。**複数の問題が併存している場合、1つ直しただけで「直った」と発表するのは早計**。

## 3. GitHubでのファイル作成ミスの反復
- 新規ファイル作成時、編集エリアが空のままコミットされる事故が複数ファイルで発生（ビルドエラー「Export doesn't exist」「Module not found」で発覚）
- フォルダの中から「+」で新規作成した際、パスが二重になる事故（`app/api/app/api/post-sukuado-promo/`）が発生
- **教訓**：GitHub UIでのファイル作成は必ずリポジトリのトップページから開始し、コミット前に中身が入っているか目視確認する運用ルールが必要

## 4. X APIトークンの401エラーの原因特定に時間を要した
権限設定（Read/Write）を先に疑ったが、実際はConsumer Key/Secret・Access Token/Secretの値自体のズレが原因だった。Vercelの環境変数は一度保存すると値を再確認できない仕様のため、**「疑わしい認証情報は個別に検証せず、まとめて作り直す」方が早い場合がある**。

## 5. 環境変数の見えなさによる非効率な往復
CRON_SECRETやSCAD_X_*の値が「保存後は閲覧不可」という仕様を知らず、確認しようとして手間取った。**機密環境変数は照合ではなく再生成で解決する運用を最初から想定しておくべき**。

# PATTERNS_CANDIDATE

## 再利用可能な設計

1. **外部副作用ごとに独立cronを立てる**：内部fetchでcronを連鎖させない。Vercel Authenticationやタイムアウト、実行時間の枠の奪い合いなど、内部fetchには複数の構造的リスクがある。
2. **slotパラメータによる共通ハンドラ設計**：`runXxx(request, slotName)`のように、投稿内容やRedisキーだけを設定オブジェクトで切り替え、ロジック本体は1本化する。
3. **標準デバッグインターフェース**：`?key=` `?dry=1` `?force=1` `?report=1`の4点セットをどんな自動投稿系エンドポイントにも実装する。
4. **Redisへの実行レポート保存**：`last_xxx_report`のようなキーに毎回の実行結果（success/error、picked item、timing）をJSON保存し、`?report=1`で取得できるようにする。ログ画面を開かずに状態確認ができる。
5. **成功後にのみ状態更新**：重複防止フラグ・ローテーションindexは、外部APIの成功レスポンスを確認してから更新する。

## 再利用可能な機能

- `weightedLength(text)`：X（旧Twitter）の重み付き文字数カウント（CJK/絵文字=2、URL=23固定）を実装した関数。X投稿を扱う全プロジェクトで再利用可能。
- `interleaveByCategory(items)`：カテゴリ・タグが偏った配列を、決定的なラウンドロビンで均等に分散させる関数。コンテンツローテーション全般に応用可能。
- `tweetWithRetry(xClient, text, attempts)`：X投稿のリトライ処理（重複エラーは再試行しない設計）。
- Meta Graph API向け`metaFetch` + `formatMetaError`：Instagram/Threads等Meta系APIのエラー詳細（code/subcode/fbtrace_id）を統一フォーマットで返す。

## 再利用可能なプロンプト

- Gemini呼び出し時の`thinkingConfig: { thinkingBudget: 0 }`設定：モデルの思考過程（"THOUGHT:"等）が出力に混入するのを防ぐ。
- 「JSON形式のみで返してください。マークダウン不要」という指示＋`safeParseJson()`（正規表現で`{...}`部分を抽出しJSON.parse、失敗時はnullを返してフォールバック値を使う）の組み合わせ：Gemini出力のパース失敗で処理全体がクラッシュするのを防ぐ定型パターン。

# BUSINESS_KNOWLEDGE

## 業務改善ノウハウ

- **プリペイド課金APIのコスト構造**：X APIはテキストのみ$0.015/件、URL付き$0.20/件（約13倍）。宣伝リンクは本文に直接入れず「プロフィールから」と誘導するC案から始め、A/Bテストで比較検討する方針が費用対効果として合理的。
- **Vercel Hobbyプランの制約変遷を把握しておく**：cron本数上限（2026年1月に全プラン100本/プロジェクトへ統一）、実行時刻のブレ（最大1時間）、Deployment Protectionの挙動（生成デプロイURLのみ保護、本番ドメインは公開）など、無料/安価プランの細かい仕様変更が設計判断に直結する。
- **GitHub Web UIでのコード管理運用ルール**：新規ファイルはリポジトリトップから作成、コミット前に中身を目視確認、長いファイルはコピーボタンを使う——という手順を徹底することで、無言の貼り付け失敗によるビルドエラーの再発を防げる。

## ドメイン知識

- **婚活・恋愛マーケティング**：データ訴求（統計・出典明記）と共感訴求（実務アドバイス）を朝夜で分けることで、単調な広告に見えない設計にできる。四半期ごとの出典データ更新、固定ポスト候補の選定（インパクトの強い統計を常設）などの運用知見。
- **Instagram/Threads APIの周期的メンテナンス**：長期アクセストークンは60日で失効するため、9月上旬などのタイミングをカレンダーで管理する必要がある。将来的には`refresh_access_token`による自動更新が望ましい。

# AI_TIPS_CANDIDATE

- **ノーコード開発フロー**：西村自身はコードを直接書かず、要件をAI（Claude/Gemini）に伝えて実装させ、動作確認を繰り返す方式でアプリ・自動化基盤を構築している。プロンプト設計とデバッグ指示の質が開発速度を左右する。
- **スクリーンショットベースの協働デバッグ**：Vercelのビルドログ・GitHub画面・環境変数設定画面などをスクリーンショットで共有し、AIがそこから状態を読み取って次の指示を出す、という反復がエラー解決に有効に機能した。
- **「レポートなしで進めて」の判断**：ログやレポートへのアクセス手段が分からない場合、無理に手順を教えるより「原因が何であれ対処できる防御的な修正」を先に実装し、後から検証する進め方が効率的な場面がある。
- **既知の失敗パターンを次のプロジェクトに継承する**：スクアド構築時、Migoronで実際に起きた事故（内部fetch問題、Redis更新順序、文字数超過等）を引き継ぎ書に明文化し、同じ轍を踏まないよう新規実装に反映した。プロジェクトをまたいだ「教訓の資産化」が有効だった。
- **AIに実装させる際の権限・認証情報の扱い**：APIキーやシークレットはチャットに貼らせず、必ず環境変数（Vercel等）経由で渡す運用を徹底することで、AIが安全にコードを書きつつ機密情報の漏洩を防げる。
