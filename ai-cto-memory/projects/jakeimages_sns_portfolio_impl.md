# PROJECT_SUMMARY

* **プロジェクト名**：motionimaging ── @jakeimages X自動投稿機能の新規実装 ＋ SNSアカウントポートフォリオ全体最適化
* **目的**：①新規Xアカウント`@jakeimages`で生成AIトレンドを自動発信し、自社アプリ（スクアド／SCADビューティー）への導線を作る ②既存3プラットフォーム6アカウントの運用を棚卸しし、露出最大化とアプリ収益化を両立させる戦略に再構成する
* **対象ユーザー**：西村氏（motionimagingjp）本人。フォトグラファー兼個人開発者。婚活AIアプリ「スクアド」、パーソナルカラー診断アプリ「SCADビューティー」を自ら運営
* **作成した機能**
  - `/api/post-jake-ai-morning` `/api/post-jake-ai-night`（Gemini＋Google検索groundingによる都度ニュース生成、静的JSON20本フォールバック、14日重複回避、曜日判定＋交互CTA）
  - `?key=` `?dry=1` `?force=1` `?report=1` の運用インターフェース
  - Vercel Cron 2本の追加登録
  - jakeimages・スクアドのThreadsクロスポスト拡張（テキストのみ・ベストエフォート）
  - SNSアカウントポートフォリオ戦略資料（現状診断＋3段階の再構成プラン、Artifactとして納品）
* **技術スタック**：Next.js (App Router) / Vercel Cron・Functions / Upstash Redis / Google Gemini API（gemini-2.5-flash, Google Search grounding） / twitter-api-v2（X API v2, OAuth 1.0a） / Threads Graph API
* **アーキテクチャ概要**：アカウント×時間帯ごとに薄いルートファイルを置き、共通ロジックは`app/api/_lib/post-*-core.js`に集約（`slot`名だけ渡す設計）。状態管理は全てRedis（次回投稿index、投稿済みフラグ、CTAローテーション、重複防止履歴）。静的コンテンツはビルド時静的import。生成AI呼び出しはSDK不使用でREST直叩きに統一。X投稿成功後にThreadsへ同文面をベストエフォートでクロスポスト（Threads失敗はX投稿の成否に影響しない）
* **達成した成果**：@jakeimages新アカウントの自動投稿基盤を実装〜本番デプロイ〜`?dry=1`実機確認まで完了（PR#1〜#3）。SNS6アカウントの現状診断と再構成戦略を策定。Threadsクロスポスト拡張を実装（PR#4）、jakeimages分は即時有効化可能な状態に到達
* **成功事例**：既存実装（sukuado-core.js／post-daily.js）のパターンを正確に踏襲したことで新機能の実装〜デバッグが高速化。段階的PR運用（新機能→本番検証→バグ発覚→即修正PR）により大きな手戻りなく本番投入
* **失敗事例**：Gemini+Google検索grounding使用時に`maxOutputTokens`を過小評価（初期値500）し、本番で常に応答が途中で切れ静的フォールバックに落ちるバグが発生。1回の修正では直らず、`finishReason`診断ログ追加という2段階の修正が必要だった。またThreads APIの「テスター追加」UIでThreadsハンドル名を入力しエラー（Facebookアカウント識別子が必要だった）となり、本会話終了時点で未解決
* **技術選定理由**：Gemini REST直叩き（SDK不使用）は既存コードベース全体との一貫性優先。Redisはステートレスな Vercel Function間で投稿状態を引き継ぐ唯一の永続化手段。動的生成＋静的フォールバックの二段構えは、ニュース系コンテンツの鮮度要求とGemini障害時の無投稿リスク回避を両立するため（引き継ぎ書で明示的に指定された設計方針）。OAuth 1.0aは既存twitter-api-v2呼び出しパターンとの互換性のため採用

# LESSONS_CANDIDATE（成功パターン）

1. 新規SNSアカウント機能は、既存の類似実装をテンプレートとしてコピーし差分のみ変更する方式が、実装速度・品質の両面で最も効率的。
2. 本番投入前に`?dry=1`で実機テストする運用を新機能にも継承したことで、デプロイ直後にトークン切れバグを検知でき、誤投稿を未然に防げた。
3. Gemini呼び出しのエラーに`finishReason`と応答文字数を含めるよう改修したことで、次の失敗原因を推測でなく事実ベースで特定できるようになった。
4. 既存アカウントの流用や新規PRのマージなど、影響範囲のある判断は都度ユーザーに一言確認してから進めることで、手戻りなく合意形成できた（例：御朱印アカウント流用前にフォロワー数・稼働状況を確認）。

# FAILURES_CANDIDATE（失敗パターン）

1. **grounding併用時のトークン予算見積もりミス**：Google検索grounding・thinking双方がトークン予算を消費することを軽視し、初期値`maxOutputTokens: 500`では常に応答が途中で切れる状態のまま本番投入した。教訓：grounding/thinking系オプションを使うGemini呼び出しは最初から余裕を持った上限（2000〜4000程度）を設定すべき。
2. **診断情報の後付け**：`finishReason`を最初のエラーハンドリングに含めていなかったため、1回目の修正（トークン上限引き上げ）だけでは原因が特定できず、2回目の修正でようやく根本原因の絞り込みができた。生成AI呼び出しは実装時点で診断情報を仕込むべき。
3. **Meta系APIのUIラベル誤読**：「Threadsテスターを追加」というラベルからThreadsのユーザー名を入力すると誤解したが、実際はFacebookアカウント識別子（名前・メール）が必要だった。UIラベルの文言だけで入力形式を判断せず、小さく試してエラーメッセージから仕様を確認する方が早い。

# BUSINESS_KNOWLEDGE（業務改善ノウハウ／ドメイン知識）

- X API投稿にはBasic以上の有料プラン（プリペイド課金）が必要。アカウントごとに別残高にする場合、Developer Portalへそのアカウント自身でログインし新規Appを作る必要がある
- Threads APIはInstagramアカウントが「ビジネス/クリエイターアカウント」である必要がある（個人アカウントのままでは連携不可）
- Threadsのアクセストークンは長期でも60日で失効するため、定期更新の運用設計が必要
- 休眠中の既存SNSアカウント（フォロワー少数・非アクティブ）を新用途に転用する判断基準：フォロワー数が少なく非アクティブなら既存フォロワーへの影響は限定的と判断できる
- 性質の異なる複数アプリ（婚活系／美容系）のCTA配分は「後発アプリほど露出を増やす」原則で見直す必要がある。実際に後発アプリのCTA露出が先発アプリより少ないという逆転現象が発生していた

# AI_TIPS_CANDIDATE（AI活用ノウハウ）

- Gemini APIでGoogle検索grounding（`tools: [{google_search: {}}]`）使用時は、通常のテキスト生成より`maxOutputTokens`に大幅な余裕（2000〜4000程度）を持たせる。grounding処理自体がトークン予算を消費するため
- Geminiの応答が期待通りでない場合、`candidate.finishReason`を必ずログ・エラーメッセージに含める。`STOP`以外（`MAX_TOKENS` `RECITATION` `SAFETY`等）は原因が全く異なり、これがないと推測でしかデバッグできない
- 「JSON形式のみで出力」を指示しても、寛容な正規表現抽出＋`JSON.parse`失敗時のtry/catchを両方備えると、フォーマット逸脱に強くなる
- ノーコードのGUI設定（Vercel・Meta Developer Portal等）をユーザーと並走して進める際は、都度スクリーンショットを共有してもらい、実際に見えているボタン名・エラーメッセージに基づいて次の一手を指示する方が、一般的な手順書の提示より速く正確に進む
