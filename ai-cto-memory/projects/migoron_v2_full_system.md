# PROJECT_SUMMARY

## プロジェクト名
Migoron（ミゴロン）SNS完全自動投稿システム

## 目的
風景・ポートレート写真家ブランド「ミゴロン」のSNS運用を完全自動化する。X（旧Twitter）とInstagram 2アカウントに、独自の「ミゴロン指数」（花・富士山・雲海・星空・お出かけ開運）とAI生成キャプションを毎日決まった時刻に自動投稿し、写真家本人の運用負荷ゼロで発信を継続する。

## 対象ユーザー
- 運用者：西村（写真家・アラフィフ・非エンジニア、AIツールで開発）
- 発信先オーディエンス：風景/ポートレート写真愛好家、旅行者、お花見・絶景スポットを探す層（日英両対応）

## 作成した機能
- **朝の統合投稿（6:03）**：花畑指数（日本語）＋Kanto Bloom Report（英語）＋お出かけ開運指数のX3投稿＋Instagram風景・ポートレート2投稿
- **夕方投稿（18:05）**：今夜の星空指数予報（月齢補正付き）
- **夜投稿（21:15）**：翌朝の雲海指数・富士山指数
- **独自指数エンジン**：気象データ×季節×六曜×月齢を掛け合わせた撮影/お出かけ適性スコア算出
- **AI画像テーマ判別**：Gemini Visionで写真を解析し、テーマ（ビーチ/星空/ダイビング等）に応じたキャプション自動生成
- **二重投稿防止**：Redisフラグ＋Instagram API直近投稿チェックの二段構え

## 技術スタック
| レイヤ | 採用技術 |
|---|---|
| ホスティング/実行 | Vercel（Hobbyプラン、cron + サーバーレス関数） |
| フレームワーク | Next.js（App Router、route.js） |
| コード/画像管理 | GitHub（raw.githubusercontentで画像配信） |
| 状態管理 | Upstash Redis（投稿済みフラグ・画像インデックス） |
| 生成AI | Gemini 2.5 Flash（テキスト＋Vision、thinkingBudget:0） |
| 気象データ | Open-Meteo（forecast/marine、無料・キー不要） |
| SNS投稿 | X API（従量課金）、Instagram Graph API |

## アーキテクチャ概要
```
Vercel cron (3本)
  ├─ post-morning-all (6:03)
  │    ├─ 1. Instagram×2 を await で完全実行（内部fetch）
  │    │      ├─ post-instagram（motion）→ Redis/Gemini/Open-Meteo/Graph API
  │    │      └─ post-jake-images（jake）→ 同上＋EXIF CSV参照
  │    └─ 2. X×3 投稿（Gemini生成→コード側で整形→X API）
  ├─ post-evening (18:05) → 星空指数
  └─ post-daily (21:15) → 雲海・富士山指数
```
- 各APIは`Bearer CRON_SECRET`で認証
- 画像はGitHubリポジトリに置き、raw URLでInstagramに渡す
- Redisで日次重複と画像ローテーション位置を管理

## 達成した成果
- X投稿（1日6本）とInstagram投稿（1日2本）の完全自動化を実現
- 5月〜7月に発生した複数の障害（X支払い・トークン失効・Vercel制約）を全て復旧
- cron 5本→3本統合でHobbyプラン（無料）を維持したまま安定運用
- 運用コストを月$2〜3（X従量課金のみ）に抑制
- 日英2言語での発信を自動化

## 成功事例
- **JSON中間層パターン**：Geminiに「数値＋短文のみJSON生成」させ、投稿本文はコード側で組み立てることで、文字数超過・書式崩れ・思考モード混入を一掃
- **Instagram先行awaitパターン**：重い処理を関数の最初に完全実行することでサーバーレスの凍結問題を回避
- **report返却デバッグ**：レスポンスに全処理結果を埋め込み、有料ログなしで原因特定を可能に

## 失敗事例
- 「投げっぱなしfetch」でInstagram呼び出し→Vercelが関数return時に処理を殺し投稿されず
- Gemini JSONパース失敗が関数全体をクラッシュさせ、以降の投稿が全滅
- cron 5本のままHobbyプランで運用→数日投稿が飛ぶ
- スマホでの部分編集でコード二重定義（igResults重複）→ビルドエラー

## 技術選定理由
- **Vercel Hobby**：無料でcron＋サーバーレスが使える。ただしcron3本・1時間遅延の制約あり
- **Gemini 2.5 Flash**：安価・高速でVision対応。thinkingBudget:0で思考出力を抑制可能
- **Open-Meteo**：APIキー不要・無料で天気/海況/hourlyが取れる
- **Upstash Redis**：Vercelと親和性が高くサーバーレスから軽量アクセス可能
- **GitHub raw配信**：別途画像ストレージ不要、Instagram Graph APIはpublic URLを要求するため好相性
- **X従量課金**：Freeプランが投稿不可になったため。月150件で$2-3と安価

## 次回改善点

2. X英語版の重複403対策をさらに堅牢化（内容差別化の自動化）

4. cron遅延を見越したリトライ機構
5. 画像の整理（GitHub直下の残骸jpg削除）

# LESSONS_CANDIDATE（成功パターン）

## L1. AIには「構造化データのみ」生成させ、整形はコードで行う
Geminiに完成文を作らせると、文字数超過・書式崩れ・思考モード混入が頻発する。「スポット名＋スコア＋短いメモをJSONで返す」に限定し、投稿文の組み立て・改行・ハッシュタグ付与はコード側で確定させると、出力が安定する。**生成AIは"素材"を作る係、整形は決定的コードが担う**という役割分担が鍵。

## L2. サーバーレスでは重い非同期処理を「最初にawaitで待ち切る」
処理をreturn後に走らせる設計（fire-and-forget）はVercelでは動かない。優先度の高い外部呼び出し（今回はInstagram）を関数冒頭でawaitして完全に終わらせ、その後に軽い処理を回す。`maxDuration`も明示して実行枠を確保する。

## L3. デバッグ情報をレスポンス本文に埋め込む
有料ログが見られない環境では、APIレスポンスに`report`オブジェクト（各サブ処理のstatus＋body先頭200字＋成否）を返すと、認証を一時的に外してブラウザアクセスするだけで全工程の状態が可視化できる。

## L4. 冪等性はダブルチェックで担保する
Redisフラグだけでなく、投稿先API（Instagram）の直近投稿タイムスタンプも確認する二重チェックにすることで、Redisが飛んでも・手動連打しても1日1回投稿を保証できる。

## L5. 個別try/catchで「1つの失敗が全体を殺さない」設計にする
複数投稿をループで回す際、各投稿を個別try/catchで囲む。1件がAPI拒否されても残りは続行し、結果をreportに記録する。JSONパースも`safeParseJson`でラップしフォールバック値を用意する。

## L6. 段階的な問い合わせ（elicitation）で要件を固める
非エンジニアユーザーとの開発では、選択肢ボタンで「スポット数・文字数・投稿順・時刻」等を一つずつ確定させると認識齟齬が減る。ただし決定は都度コード全体を出して確実に反映する。

# FAILURES_CANDIDATE（失敗パターン）

## F1. fire-and-forget fetch（投げっぱなし呼び出し）
```js
// ❌ Vercelでは届く前に殺される
fetch(url).catch(() => {});
return Response(...);
```
→ サーバーレスは関数returnで処理凍結。必ず`await fetch(url)`で待つ。

## F2. 生成AIの出力を直接parseして関数全体が死ぬ
```js
// ❌ 不正JSONで例外→以降全滅
const parsed = JSON.parse(raw);
```
→ try/catchでラップし、失敗時フォールバック。`safeParseJson`パターン化。

## F3. cron本数がプラン上限を超過
Hobbyプランはcron 3本まで。5本登録すると一部が無言で実行されず、数日投稿が飛ぶ。→ 複数処理を1エンドポイントに統合。

## F4. 天気APIのdaily値をそのまま使う
Open-Meteoのdailyは1日の最悪値。夜に雨予報だと日中晴れでも「雨」表示に。→ hourlyで必要な時間帯（朝6-20時等）だけ抽出。

## F5. 外部トークンの有効期限を失念
Instagram長期トークンは60日で失効。運用が突然止まる。→ 期限をカレンダー管理、将来は自動更新実装。

## F6. スマホ部分編集によるコード破損
部分diff貼り付けで新旧コードが二重化（変数の重複宣言）・文字列途中切れ。→ ファイル全体を「削除→新規作成」で置換。

## F7. 同一内容の連続投稿でSNSが重複拒否
Xは同日の類似内容を403で弾く。手動テスト連打で頻発。→ 日英で本文構造（タイトル・番号形式・タグ）を差別化。自動実行1回なら問題なし。

# PATTERNS_CANDIDATE

## 再利用可能な設計

### P1. 統合オーケストレーターパターン
1つのcronエンドポイントが、認証付き内部fetchで複数の専用APIを順次呼ぶ。プラン制約（cron本数）を回避しつつ、各APIは単独テスト可能なまま維持できる。重い処理を先、軽い処理を後に配置。

### P2. 指数エンジンの分離
「気象データ取得 → 補正ロジック（季節/六曜/月齢）→ スコア算出 → 表示整形」を関数分割。データソースと表示を疎結合にすることで、天気APIの範囲変更やスコア基準の調整が局所修正で済む。

### P3. 画像ローテーション＋日次ロック
Redisに「フォルダ切替カウンタ」「各フォルダの現在インデックス」「本日投稿済み日付」を持たせ、画像を順番に消化しつつ二重投稿を防ぐ。画像はGitHub raw URLで配信。

### P4. 天文計算の内製化
日の出/日没/六曜/月齢/積算温度を外部APIに頼らずコードで算出（julianDay関数ベース）。API依存を減らし、無料・高速・オフライン計算可能に。

## 再利用可能な機能

- `safeParseJson(raw)`（AI出力の安全なJSON抽出：コードブロック除去＋正規表現抽出＋try/catch）

# BUSINESS_KNOWLEDGE

## 業務改善ノウハウ

- **投稿の役割分担で重複を防ぐ**：同じテーマ（花）を朝と夜の両方で出すと、同日重複でSNSに弾かれる。時間帯ごとに扱うテーマを分離する（朝=花/開運、夕=星空、夜=雲海/富士）。
- **無料枠を守る統合設計**：機能追加＝cron追加ではなく、既存エンドポイントへの相乗りで無料プランの上限内に収める。コスト意識を設計段階で持つ。
- **非エンジニア運用を前提にした復旧手順書化**：トークン更新・環境変数変更・Redeployの手順を明文化。障害時に本人が対応できる状態を保つ。
- **失効する認証情報のカレンダー管理**：60日トークンなど期限のある資格情報は、失効前提でリマインダー化。突然の停止を防ぐ。

## ドメイン知識

- **積算温度による開花予測**：桜は2/1起算で積算温度210℃で開花、370℃で満開の目安。桜期のみこのアルゴリズム、他の花は季節テーブルで代替。
- **六曜・選日**：大安/仏滅等は julianDay%6 で算出可能。一粒万倍日・天赦日は月ごとの干支番号テーブルで判定。お出かけ/開運系コンテンツに有効。
- **月齢と星空撮影**：新月前後が天の川撮影に最適。月齢で星空指数を±補正すると説得力が増す。
- **雲海の発生条件**：放射冷却・湿度・風速・露点と最低気温の差が判断材料。曇天でも薄い雲海の可能性を明記できる。
- **Instagram Graph API**：public URL画像が必須（GitHub rawが好相性）。container作成→publishの2段。長期トークンは60日失効・更新可能。
- **X API課金体系**：Freeは投稿不可。従量課金でテキスト$0.015/件、URL付き$0.20。テキスト主体にするとコスト最小。

# AI_TIPS_CANDIDATE

## AI活用ノウハウ

### T1. 生成AIは「非決定的な素材生成」に限定し、決定的処理はコードに寄せる
文字数・書式・順序など「守ってほしいルール」はAIに任せず、コードで確定させる。AIには創造的な文章・スコアの推定だけを担わせる。これで出力の再現性と品質が安定する。

### T2. Geminiの思考モードは二重で抑制する
`generationConfig.thinkingConfig.thinkingBudget = 0` を設定し、さらにレスポンスの parts から `!p.thought` のテキストのみを抽出する。片方だけだと思考文が混入することがある。

### T3. Vision判別は「選択肢を固定」して安定させる
画像分類は自由回答でなく、あらかじめ定義したラベル群から1つ選ばせる。後続のテンプレート分岐に確実に接続できる。

### T4. AI出力は必ず「壊れる前提」で受ける
JSONパースはtry/catch＋フォールバック必須。正規表現でJSON部分だけ抽出（前後の余計な文字を除去）してからparseする。

### T5. プロンプトに具体的な出力例（few-shot）を1つ入れる
期待する形式の実例を1つ示すと、書式順守率が大きく上がる。特にJSON構造は完全なサンプルを提示する。

### T6. 非エンジニアとのAI開発は「全文出力＋削除→新規作成」で事故を防ぐ
部分diffは貼り付けミス・二重定義の温床。毎回ファイル全体を出力し、既存を全削除してから貼り付けてもらう運用が最も確実。

### T7. デバッグは「レスポンスに状態を吐かせる」のが最速
ログ環境が貧弱でも、APIが自分の処理結果を構造化して返せば、ブラウザで叩くだけで原因が見える。認証を一時的に外す運用とセットで強力。
