# PROJECT_SUMMARY

- **プロジェクト名**：スクアド（SCAD / SCAD CHAT）※前身：婚活船長ジェイ（konkatsu-jay）
- **目的**：LINEやマッチングアプリのスクリーンショット・テキストをAIが分析し、関係性ステージや相手の熱量を判断した上で、返信メッセージ・送信タイミング・デートプラン等を提案する恋愛・婚活支援AIチャットアプリ。特許出願済み（特願2026-190649「コミュニケーション支援装置」）の技術思想を将来的に実装する計画あり。
- **対象ユーザー**：マッチングアプリ・婚活中の男女（30〜50代中心）。3人のAIアドバイザー（サキ＝共感型、レン＝行動派、のり様＝経験豊富な大人）でユーザー層を切り分け。
- **作成した機能**
  - スクショ＋テキスト＋返信キーワードの複合入力によるメッセージ添削・分析
  - 3アドバイザー制チャットUI（DECODE風・LINE風バブル）
  - デートレストラン提案アプリ（エリア・予算・ジャンル指定→3店舗提案）
  - 関係性スコア化機能（のり様担当・段階的ヒアリング形式）
  - Google Analyticsによるアクセス計測
  - PWA化（ホーム画面追加・鳥居×八咫烏アイコン）
  - 独立した「このアプリについて」ページ（開発者紹介・データ取扱い・SCADシリーズ連携・SNS）
  - プライバシーポリシーページ
- **技術スタック**：Next.js 14 (App Router) / React / Vercel（ホスティング・Analytics） / GitHub（手動デプロイ） / Google Gemini API（gemini-2.5-flash、有料プラン）
- **アーキテクチャ概要**：現状はブラウザ→Gemini API直接呼び出し（APIキーはNEXT_PUBLIC環境変数でクライアント露出）。将来的に特許思想（中間サーバーでメタデータ抽出→Geminiには演算結果のみ渡す）に基づき、中間サーバー＋DB（Supabase想定）を挟む設計へ移行する計画が合意済み（未着手）。
- **達成した成果**
  - ゼロから1日でWebアプリを2本（konkatsu-jay, スクアド）設計・公開
  - 特許出願完了により公開制約が解除され、開発加速
  - ユーザーの実使用フィードバックに基づく複数回のUI/UX改善サイクルを完走
- **成功事例**：LESSONS_CANDIDATE 参照
- **失敗事例**：FAILURES_CANDIDATE 参照
- **技術選定理由**
  - Next.js＋Vercel：GitHubアップロード→自動デプロイの手軽さ、無料枠、環境変数管理のしやすさ
  - Gemini API：DECODEでの実績、無料枠→有料転換のコスト試算のしやすさ（1回約0.07円）
  - PWA：ネイティブアプリ開発（審査・Swift書き直し・年間費用）を回避しつつアプリライクな体験を実現
- **次回改善点**：中間サーバー化（Phase1）、Supabase導入によるデータ保存（Phase2）、メタデータ演算・待機時間算出の実装（Phase3）。Gitブランチによる開発/本番環境の分離。

> 注記: `sukuado_decode_app.md`では「スクアード（前身：DECODE）」とされているが、本ファイルでは「前身：婚活船長ジェイ」とされている。アドバイザー制（サキ・レン）はDECODE系、レストラン提案機能は婚活船長ジェイ系の踏襲と見られ、両系統が合流して現行のSCAD CHATになった可能性が高い。正確な系譜はユーザーに要確認。

# LESSONS_CANDIDATE

- 段階的にリリースし、実際に使いながら機能を育てる方針が有効だった（シンプル版から徐々にアップデートする判断を追認し実行）
- ユーザーの実利用シーン（スクショ＋自分で考えた返信キーワードを同時に入れたい）をヒアリングしてから機能設計すると、仕様が使いやすくなる
- UI崩れのデバッグは「疑わしい原因を1つ直して確認」ではなく「確実に見える場所に配置し直す」方が早く解決する（ヘッダー右上ボタンの表示不具合を、独立した横長バーへの移動で解決）
- チャットAIの応答は「段階的開示」設計にすると体験が向上する：①短い会話→②深掘り提案→③詳細フォーマット（見出し3つ限定）
- 他アプリ（DECODE, SCAD BEAUTY）の実装済みUIパターンを引き継ぎ書化して横展開することで、デザイン・機能の一貫性（シリーズ感）を効率よく作れた
- 本番運用中のアプリは、開発中の変更で壊さないようブランチ分離すべきという提案を先回りして行えた
- データの学習利用有無など、事実確認が必要な文言は必ずWeb検索等で裏取りしてから記載する
- 特許出願の有無で開発方針の自由度が変わるため、法的手続きの進捗を都度確認しながら機能実装の順序を決める判断が機能した

# FAILURES_CANDIDATE

- GitHubへのファイルアップロードでフォルダ構造の理解不足によるトラブルが複数回発生（`public`フォルダのつもりが単一ファイル化、`page.js`が2つ並列でアップロードされフォルダ階層が壊れる等）
- Geminiのモデル名指定を都度誤り、非推奨モデル使用によるエラーを複数回発生させた（`gemini-2.0-flash`→廃止→`gemini-2.0-flash-001`→廃止→`gemini-2.5-flash`）。事前にWeb検索で最新モデル名を確認すべきだった
- 無料APIキーの割り当て制限（quota）を実運用開始前に確認せず、有料化の手続きも「Google Cloud」と「Google AI Studio」の課金設定を混同し、ユーザーを何度も往復させた
- GitHub Personal Access Tokenを使った自動化を提案したが、実際には環境上GitHubへの書き込み権限がなく実現不可能だった。事実確認せずに「できる」と答えたことが原因
- PWA化のstatusBarStyle設定（black-translucent）がヘッダーレイアウト崩れの一因になった可能性が高いにもかかわらず、原因特定に時間がかかった
- 命名変更（「ジェイ」→「のり様」等）の影響範囲を機械的に洗い出す仕組みがなく、都度grepで手動確認する運用になっていた

# PATTERNS_CANDIDATE

**再利用可能な設計**
- 3アドバイザー（共感型／行動派／経験者）+ ユーザーによる手動選択、という役割分担モデル。`name / emoji / color / tagline / greeting / quick / prompt` を1オブジェクトにまとめる設計は再利用性が高い
- クイックボタン（悩みの入口）をアドバイザーごとに変えることで、同じチャットUIでもターゲット層を分けられる
- 「このアプリについて」ページの構成テンプレート：①開発者の顔・タグライン→②機能紹介→③データ取扱い（安心材料）→④シリーズ導線→⑤連絡先
- 「姉妹アプリ一覧」を配列データ1つで管理し、`kind: current/external/soon` で表示分岐する設計

**再利用可能な機能**
- スクショ＋テキスト＋自由記述キーワードを1つの入力エリアに統合し、AIが自動判断（受信履歴／下書き／キーワードのいずれか）で対応を変える入力UI
- 段階的ヒアリング→スコア化という、複数ターンかけて情報収集してから診断結果を出すプロンプトパターン
- チャット内Markdown記号混入の二重対策（①プロンプトで明示的に禁止、②表示前に正規表現で強制除去）

**再利用可能なプロンプト**
- 「まず短く共感→深掘りの余地があれば一言提案→ユーザーが望めば見出し3つ以内の詳細フォーマット」という3段階レスポンス設計プロンプト
- 「アスタリスクや見出し記号などのMarkdown記法を一切使わない」という文体指定を全アドバイザー共通の指示として分離する設計

# BUSINESS_KNOWLEDGE

- 婚活・恋愛相談アプリでは、未成年をターゲット層に含めることは設計思想上のリスクが大きい（関係進展を後押しするAIの性質上、相手が誰であれ危険性が生じるため）
- 「占い」的要素（今日の運勢等）は間口を広げる効果があるが、実際にAIが答えられない/答えるべきでない内容は早期に見直しが必要
- ユーザー個人の婚活経験を売り文句に使うことに対し、本人が「恥ずかしい」と感じる場合はAIの応答文言から外し、Webの自己紹介文言にとどめるという線引きが有効だった
- Gemini APIのコストは実際には極めて低い（1回あたり約0.07円）ため、「利用回数制限」より「まず無料開放して認知を広げる」判断が、認知度ゼロのフェーズでは合理的
- Vercelの「ドメイン」は同一プロジェクトに複数割り当てられ、単なる別名（エイリアス）に過ぎない。「開発環境」を分離するには、ドメインではなくGitのブランチ機能を使う必要がある
- 個人開発者が複数アプリを運営する際、「このアプリについて」ページに姉妹アプリへの導線を作ることで、個別アプリではなく「シリーズ」としての信頼感を演出できる

# AI_TIPS_CANDIDATE

- モデル名・API仕様など「現在の状態」に関わる情報は、コードを書く前に必ずWeb検索で最新情報を確認する。過去の学習知識だけで実装すると非推奨モデルエラー等を繰り返し引き起こす
- 「できます」と即答する前に、自分の実行環境の権限・制約（例：外部APIへの書き込み可否）を確認する。憶測で機能提供を約束すると、ユーザーに無駄な作業をさせるリスクがある
- 非エンジニアのユーザーにGit/GitHub操作を依頼する際は、スクリーンショットを都度確認しながら1ステップずつ進める方が、まとめて手順書を渡すより成功率が高い
- UIの不具合報告を受けたら、「コード上は正しいはず」という思い込みで深追いする前に、まずレイアウト上「絶対に隠れない場所」に要素を移動する荒療治を試す方が早く解決することがある
- 同じ修正を何度も繰り返す場合、対症療法ではなく設計自体を疑う
- ユーザーの過去のやり取り（メモリ）を横断的に参照し、別チャットで進行中の関連プロジェクトとの重複や役割分担を都度明示することで、プロジェクトの分散・混乱を防げる
- ユーザーが提示した「他アプリの引き継ぎ書」形式の資料は、そのまま模倣するのではなく、実装対象アプリの実データに忠実に書き換えることが重要
