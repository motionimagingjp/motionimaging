# AI-CTO-Memory：SCAD Beauty（HAIR Recipe）プロジェクト

> このプロジェクト傘下の全チャットを横断分析して統合した、西村様専用のAI-CTOメモリです。

---

# PROJECT_SUMMARY

- **プロジェクト名**：スクアド ビューティ（SCAD Beauty／旧称 HAIR Recipe）
- **目的**：婚活・写真撮影事業に紐づき、30〜50代の恋活・婚活層に向けて、髪型・ファッション・レストランのAIアドバイスを提供する。コンセプトは「スクアド＝スクショでアドバイス」＝写真やスクショをアップするだけでAIが即答すること。
- **対象ユーザー**：恋活・婚活サービスの利用者（メンズ・レディース両対応）。オーダーシートを受け取る美容室スタッフも間接ユーザー。
- **作成した機能**：
  - **ヘアタブ**：顔型診断（自撮り／自己申告／スキップ）、18パターンのプリセットカタログ、参考画像アップロード解析、AIヘアマッチング（自撮り＋スタイル説明での合成試着）、オーダーシート自動生成、外部生成AI向けプロンプト自動生成
  - **ファッションタブ**：ファッションチェック（今日の服スクショ→色・靴アドバイス）／色コーデ（テイスト・パーソナルカラー・手持ち色→AI提案）の2モード。色の組み合わせ提案と靴アドバイスを必須要素化
  - **レストランタブ**：カテゴリ→ランチ/ディナー→エリア自由入力→予算→AI推薦のチャット型フロー。デート観点（個室・禁煙・カウンター・ドリンク・夜景）をGoogle Search grounding＋「要確認」フォールバックで提示。地図リンク付き
  - **共通**：性別トグル（切替時に会話全リセット）、運営者Aboutページ（`APP_ABOUT`共通フォーマット、姉妹アプリ「SCAD CHAT」にも流用）、アプリアイコン（トリカラーリボンS字デザイン）
  - （試作後に方針転換で廃止）Web検索による類似画像補完機能
- **技術スタック**：単一HTML/CSS/vanilla JS（`public/index.html`）、Vercel Serverless Functions（Node.js ESM）、Gemini API（`gemini-flash-latest`）、GitHub＋Vercel自動デプロイ、Playwright E2E検証
- **アーキテクチャ概要**：フロントは状態オブジェクト管理のSPA。`/api`配下のVercel Serverless FunctionsがGemini APIを呼び出し、フロントは`fetch()`で本番APIを試行→失敗時は既存モックへ自動フォールバック。APIキーはVercel環境変数のみで保持しフロントに非露出。
- **達成した成果**：
  - プロトタイプ検討から本番稼働（`scad-beauty.vercel.app`）まで到達
  - 顔型診断・ファッション解析・レストラン推薦のGemini API実運用化
  - 著作権・肖像権リスクのある機能（Web検索画像表示）の早期発見と全面廃止
  - モデルバージョン陳腐化問題への恒久対策（`-latest`エイリアス採用）
  - 姉妹アプリ（SCAD CHAT）へのAboutページフォーマット横展開
- **成功事例**：
  - fetch→モックフォールバック設計により、API未設定・障害時もアプリが壊れない
  - `-latest`エイリアス採用でモデル404エラーを恒久的に回避
  - ユーザーからの「バージョン確認をして」という指摘を機に、毎回Web検索で最新情報を検証する運用に転換し、Google Custom Search APIの新規受付終了という重大情報を事前把握
  - Playwrightでの機能追加・削除ごとのE2E確認により不具合を未然防止
- **失敗事例**：
  - 著作権・肖像権リスクを検討せずにWeb検索画像表示機能を作り込み、後から全面廃止（手戻り大）
  - Geminiモデル名を個別バージョン固定し、2度の404エラー（モデル廃止）を招いた
  - 非技術者への「本番ファイルをコピペして」という指示が伝わらず、複数回のやり取りが発生（「意味がわからない」というフィードバックあり）
  - 複数の並行チャットセッションが同一の`index.html`を独立編集し、マージ調整が繰り返し必要になった
- **技術選定理由**：
  - 生成AI画像編集は自社実装せず、外部ツール（Gemini/ChatGPT）向けプロンプト生成に留める（コスト・品質保証・肖像権リスク回避）
  - 画像解析はユーザー要望によりGemini API採用
  - モデル名は`-latest`エイリアスを採用（バージョン管理コスト削減、404回避）
  - ヘアマッチングは当初の2枚合成方式から、単一自撮り＋テキスト説明方式へ変更（複雑さ低減、ユーザー指摘による軌道修正）
- **次回改善点**：
  - 新機能着手前に著作権・肖像権・利用規約リスクを確認する工程を開発フローに組み込む
  - 外部AIサービスのモデル名は初回実装時から自動更新エイリアスを優先する
  - 非技術者向け操作手順は、最初から最も再現性の高い方法（例：ターミナルコマンド一発）を案内する
  - 複数チャットセッションで同一ファイルを編集する際は、作業前に「今どのファイルが最新か」を必ず確認する運用を徹底する

# LESSONS_CANDIDATE（成功パターン）

- 本番APIを`fetch()`で試行し、失敗時は既存モックへ自動フォールバックする設計により、APIキー未設定・通信障害時でもサービスが壊れない状態を維持できた
- AIモデル名にGoogleの`-latest`系エイリアスを使うことで、モデル廃止による404エラーを継続的に回避できる設計にできた
- 「バージョン間違いが頻発するので確認してほしい」という指摘を受け、思い込みで進めず毎回Web検索で最新情報を検証する運用に転換した結果、「Google Custom Search APIが新規利用不可」という重大情報を事前把握できた
- Playwrightで実際のブラウザ操作をシミュレートし、コンソールエラー・導線を毎回検証してから公開する運用により、機能追加・削除時の不具合を未然防止した
- 非技術者ユーザーへの手順案内で、詰まった時点のスクリーンショットを都度確認しながら次善策に切り替える対応が最終的にうまくいった
- インタラクティブなクリック可能プロトタイプを先に作り、見た目と使い勝手を確認してから本番実装に進むスタイルにより、手戻りの少ない要件確定ができた
- 機能要件をヒアリング段階で「まだ何もしないで」と止めてから全項目を出し切り、まとめて確認してから実装する進め方により、実装後の大きな仕様変更を防げた

# FAILURES_CANDIDATE（失敗パターン）

- Web検索で外部サイトの画像を取得しアプリ内に表示する機能を、著作権・肖像権リスクの検討をせずに先に実装してしまい、UI・モーダル・出典表記まで作り込んだ後に機能自体を全面廃止する手戻りが発生した。本来は機能設計の初期段階で法務リスクを洗い出すべきだった
- Geminiのモデル名を個別バージョン（`gemini-2.0-flash`→`gemini-3.6-flash`）で固定してしまい、本番稼働後に2度にわたり404エラー（モデル廃止）が発生した
- 「本番ファイルをここに貼ってほしい」という指示が非技術者に伝わらず、「意味がわからない」というフィードバックを受けて手順を1から丁寧なステップ形式に組み直す必要が生じた。最初から画面操作ベースの詳細ステップで案内すべきだった
- 複数の並行チャットセッションが同一の`index.html`を独立に編集しており、どちらが最新かの確認・マージ作業が繰り返し必要になった
- Google Custom Search APIについて、検証せずに「おすすめ」として案内しかけた（ユーザーの再確認要求で検証し、実際は新規利用不可だったと判明。実害前に訂正）

# PATTERNS_CANDIDATE

### 再利用可能な設計
- 「フロントが本番APIを`fetch()`で試行し、失敗時は既存モックにフォールバックする」構成（他のAI機能実装へ横展開可能）
- Vercel Serverless Functions＋環境変数でのAPIキー管理（フロントに一切キー非露出）
- カテゴリ切替時（性別トグルなど）に会話・状態を全リセットするUXパターン（複数コンテキストが混在するチャットアプリで有効）
- クイック選択チップの即時実行UI（送信ボタンを介さない一手アクション）
- 「クロスタブ提案はしない」方針（各機能タブは独立。下部メニューで既にタブ切替可能なため、タブ間誘導は冗長でユーザー体験を損なう）
- 運営者Aboutページの`APP_ABOUT`共通オブジェクト構造（ヘッダー／私について／このアプリについて／個人情報の取扱い／シリーズアプリ紹介／SNS、の6セクション構成）→姉妹アプリへそのまま横展開可能

### 再利用可能な機能
- 顔型診断（自撮りアップロード／自己申告／スキップの三択パターン）
- アップロード画像解析→既存カタログへのマッチングフロー
- ファッションの「今日のコーデ相談」機能（当日着用する服の写真→AIが色・靴アドバイス）＝「スクショでアドバイス」コンセプトの中核パターン
- レストランのチャット型絞り込みフロー（カテゴリ→時間帯→エリア自由入力→予算→AI推薦→追加絞り込み）
- Google Search grounding＋「要確認」フォールバックによる、検証不能情報の誠実な提示パターン

### 再利用可能なプロンプト
- Gemini Vision APIへの画像分類プロンプト：候補リストを明示的に列挙し「必ず次のJSON形式のみで回答」と出力形式を固定する手法
- 画像内テキスト（名前・店名・SNSハンドル・ロゴ・電話番号等）を無視し、視覚的特徴のみで判断させる指示（誤判定防止）
- 外部生成AIツール向けプロンプトの自動生成テンプレート（人物写真の髪型のみを変更する指示＋正面/サイド生成の指定）

# BUSINESS_KNOWLEDGE

### 業務改善ノウハウ
- 新しい画像関連機能を検討する際は、実装前に「著作権・肖像権・利用規約」の3点を必ず確認するステップを設ける
- ホスティングサービス（Vercel Hobbyプラン等）のログ機能は無料プランでは保持期間がほぼゼロなので、障害調査時はブラウザのDevTools Networkタブから実際のレスポンスを取得する方が確実
- 非技術者ユーザーへの手順案内は、UIベースの操作より、可能であればターミナルコマンド一発で完結する方法の方が再現性が高い場合がある
- 複数チャットセッションで同一コードベースを並行編集する場合、デプロイ前に必ず「どのファイルが最新か」のマージ状態を確認する

### ドメイン知識
- 検索エンジン以外の一般アプリが第三者サイトの画像を複製・表示する行為は、著作権法上の複製権・公衆送信権侵害にあたり得る（検索エンジン向けの著作権法47条の5の特例は対象外）
- ヘアスタイルという「型」自体の著作権保護は弱いが、その髪型を撮影した「写真」は撮影者の著作物として保護され、写っているのは実在の第三者であるため肖像権リスクも伴う
- Google Custom Search APIは2026年時点で新規顧客の受付を終了しており、既存ユーザーも2027年1月1日までに他手段（Vertex AI Search等）への移行が必要
- 美容室・ヘアスタイル関連ビジネスでは、他店の画像の無断利用や撮影同意を得ていない顧客写真の掲載がトラブルの火種になりやすい
- 「お客様自身が見つけた参考画像をアップロードして解析する」方式は、紙焼き写真を美容室に持ち込む従来の実務慣行に相当し、著作権・肖像権上のリスクが低い代替案として機能する

# AI_TIPS_CANDIDATE（AI活用ノウハウ）

- AIモデルのバージョン名は個別指定せず、可能な限り「-latest」等の自動更新エイリアスを使うことで、モデル廃止による障害を継続的に回避できる
- AIに「バージョン・仕様が最新か確認してから進めて」と明示的に指示しておくと、学習データの古い知識に基づく誤情報（廃止済みAPIの推奨など）を未然に防げる
- Vision APIへの分類プロンプトは、選択肢を明示的に列挙し「JSON形式のみで回答」と出力フォーマットを強く指定することで、パース失敗を防げる
- 生成AI画像編集そのものを自社実装するのではなく、外部ツールに貼り付けるプロンプトを自動生成する設計は、コスト・品質保証・肖像権リスクを回避しつつ「試したい人だけ試せる」導線を提供できる有効な代替案
- ブラウザ自動化テスト（Playwright等）を機能変更のたびに実行し、コンソールエラーと導線を確認してから公開する運用は、UIの繰り返し変更を伴う開発で不具合の見逃しを防ぐ
- 複雑な要件は「まだ何もしないで、まず全部聞き出して」と伝え、要件を出し切ってから一括で実装方針を確認してもらうと、後戻りの少ない実装になる

# USER_FEEDBACK（ユーザー評価）

- 「本番ファイルをここに貼ってほしい」という説明が伝わらず「意味がわからない」というフィードバックがあった → 非技術者向け説明は具体的な画面操作ステップに落とし込む必要がある、という教訓につながった
- ヘアマッチングの2枚合成方式について、複雑さを避けたいという意図から単一自撮り＋テキスト説明方式へ変更する判断があった
- 色コーデ機能で「固定の色相性テーブル」ではなくAI判断ベースにしてほしいという明確な方向修正があった（「無限のパターンは作れない」という理由）
- ヘアタブとファッションタブの連携について、「見にくくなる／混乱する」という理由で明確に非連携の判断があり、既存の「クロスタブ提案はしない」方針と一致することを確認できた
