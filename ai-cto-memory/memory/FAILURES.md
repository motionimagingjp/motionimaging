# FAILURES.md

> 失敗パターン（症状 → 原因 → 対策）。2件以上のプロジェクトで再現したものを優先し、根拠プロジェクトを併記する。
> 統合元：ai-cto-memory/projects/ 配下10ファイル（2026-09-03時点）

## F1. サーバーレス関数でのfire-and-forget（投げっぱなし）fetchは実行されない
- **症状**: Instagram投稿等が実行されず、投稿が飛ぶ
- **原因**: `fetch(url).catch(()=>{})` のように結果を待たずにreturnすると、Vercelが関数return時に処理を凍結する
- **対策**: 優先度の高い外部呼び出しは関数冒頭で`await`し、完全に終わらせてから軽い処理に進む。`maxDuration`も明示する
- 根拠: Migoron（複数スナップショットで確認）, スクアード/Migoron統合版

## F2. AI（Gemini）のJSON出力を直接parseすると失敗時に処理全体がクラッシュする
- **症状**: 1回のパース失敗で以降の投稿・処理が全部止まる
- **原因**: `JSON.parse(raw)`を try/catch なしで直接呼び出している
- **対策**: `safeParseJson()`（正規表現でJSON部分を抽出→parse→失敗時はnullでフォールバック）でラップし、複数処理をループする場合は個別try/catchで1件の失敗が全体を殺さないようにする
- 根拠: Migoron（複数スナップショット）, スクアードX/Migoron引き継ぎ, jake_images（寛容な抽出+try/catch）

## F3. 内部fetch（サーバー間の自己呼び出し）はVercel Authenticationで401になる
- **症状**: 特定の投稿（Instagram等）だけが止まる。表面的な仮説（タイムアウト等）で一度「解決」と誤認しやすい
- **原因**: Vercel Authentication（Standard Protection）がサーバー間fetchを保護対象にしている
- **対策**: 内部fetchでcronを連鎖させず、外部副作用ごとに独立cronエンドポイントを立てる設計に統一する
- 根拠: Migoron（複数スナップショットで原因特定に複数回の調査を要した）, スクアード/Migoron統合版

## F4. AIモデル名の決め打ちにより、モデル廃止のたびにエラーが発生する
- **症状**: 404エラー、原因不明のエラーが本番稼働後に繰り返し発生
- **原因**: `gemini-1.5-flash`／`gemini-2.0-flash`等、個別バージョン名をコード内に固定していた
- **対策**: `-latest`エイリアスを使う、もしくはモデル名を1箇所の定数にまとめておく。エラー発生時はまず利用可能なモデル一覧を取得して確認する運用にする
- 根拠: SCAD Beauty（2度の404）, スクアード/DECODE v2（4回のモデル変更対応）, Migoron/DECODE（早期スナップショットでも同様の失敗）, SCAD CHAT（`gemini-2.0-flash`→`gemini-2.0-flash-001`→`gemini-2.5-flash`と2段階で廃止に追われた）

## F5. X投稿の文字数制限を`text.length`で数えると重み付き仕様とズレる
- **症状**: 一部の投稿だけが時々抜ける／弾かれる
- **原因**: Xの280字制限は実際には重み付き（CJK・絵文字=2、URL=23固定）だが、`text.length`ベースで計算していた
- **対策**: `weightedLength()`を実装し、全言語・全投稿に適用する
- 根拠: Migoron/スクアードX統合版（複数箇所で確認）

## F6. Redis等の状態更新を投稿・処理の成功前に行うとデータ不整合が起きる
- **症状**: 投稿が丸ごと消える／2回目実行時に別フォルダへ誤投稿される
- **原因**: インデックス計算・フラグ更新を投稿処理より先に（または途中で）行っている
- **対策**: フラグ・インデックスの確定は投稿成功を確認した「後」にのみ行う原則を全エンドポイントで統一する
- 根拠: Migoron（複数スナップショットで繰り返し確認）

## F7. 非技術者による部分編集・複数セッションの並行編集でコードが破損する
- **症状**: 変数の二重定義によるビルドエラー、どちらが最新か分からなくなるマージ事故
- **原因**: 部分diffの貼り付けミス、または複数チャットセッションが同一ファイルを独立に編集
- **対策**: コードは常に全文で受け取り「削除→新規作成」で置換する。複数セッションで同じファイルを触る場合は、作業前に最新版を確認する運用を徹底する
- 根拠: Migoron（スマホ部分編集事故）, SCAD Beauty（並行編集のマージ事故）

## F8. GitHub Web UIでのファイル・フォルダ管理ミスが繰り返し発生する
- **症状**: ビルドエラー（「Export doesn't exist」「Module not found」）、意図しない場所へのファイル配置
- **原因**: ブラウザ版GitHub UIでの新規作成・アップロード操作でフォルダ階層を誤解しやすい（`public`フォルダのつもりが単一ファイル化される、フォルダ内「+」で新規作成するとパスが二重になる、画像をリポジトリルートに誤配置する等）
- **対策**: ファイル作成は必ずリポジトリのトップページから開始し、コミット前に中身とパスを目視確認する運用ルールを徹底する
- 根拠: Migoron（複数スナップショット）, SCAD CHAT（`public`フォルダ誤配置、`page.js`の重複アップロード）

## 個別事例（単一プロジェクトのみで確認・今後の参考）

- **著作権・肖像権リスクを検討せずに機能を作り込み、後から全面廃止**：Web検索画像表示機能をUI・出典表記まで作った後に廃止（SCAD Beauty）。新規の画像関連機能は着手前に著作権・肖像権・利用規約を確認する工程を持つべき
- **特許戦略とプロダクト実装の齟齬に後から気づく**：「本文をAI学習に渡さない」という主張と実装（会話履歴のDB保存）が矛盾していた（スクアード/DECODE）。法務・特許関連の方針転換は実装レビューと同時に必ずすり合わせる
- **FlutterFlow無料プランの制約（数値手入力不可・条件分岐不可）で開発が頓挫**：iOS版はWeb優先に方針転換（スクアード/DECODE iOS版）
- **X Developer Portalでのアカウント取り違え／OAuthバージョン取り違え**：マルチアカウント運用時は画面上部のアカウント名表示を都度確認する必要がある（スクアードX）
