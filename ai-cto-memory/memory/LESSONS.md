# LESSONS.md

> 成功パターン。2件以上のプロジェクトで再現したものを優先し、根拠プロジェクトを併記する。
> 統合元：ai-cto-memory/projects/ 配下10ファイル（2026-09-03時点）

## 1. AIには「構造化データ（数値・短文・JSON）のみ」生成させ、組み立て・整形はコードで行う
文字数超過・書式崩れ・思考モード混入は、Geminiに完成文をそのまま作らせると必ず起きる。
「スポット名＋スコア＋短文をJSONで返す」等に限定し、投稿本文の組み立て・改行・ハッシュタグ付与はコード側で確定させると出力が安定する。
- 根拠: Migoron（JSON中間層パターン／Vision複数タスク統合）, SCAD Beauty（Vision分類のJSON形式限定）, jake_images（厳格なJSON出力指定）

## 2. 状態（Redisフラグ・インデックス等）は「成功後にのみ」更新する
投稿・処理の成功を確認する前にフラグやインデックスを進めると、失敗時にデータが丸ごと消えたり、別フォルダへの誤投稿が起きる。
- 根拠: Migoron（複数スナップショットで繰り返し確認された原則）

## 3. デバッグ用クエリパラメータ（`?key=` `?dry=1` `?force=1` `?report=1`）を標準装備する
無料/安価プランでログが見にくい環境では、アプリ自身に観測可能性を持たせることで有料ログなしで運用できる。1プロジェクトで確立した後、新規プロジェクトにそのまま横展開できた。
- 根拠: Migoron → スクアードX → jake_images へと横展開

## 4. 外部副作用ごとに独立したcronエンドポイントを立て、内部fetchで連鎖させない
親cronが子cronを内部fetchで呼ぶ構成は、認証保護（後述FAILURES参照）やタイムアウトの温床になる。1機能＝1cron＝1エンドポイントの原則を横展開した。
- 根拠: Migoron → スクアードX

## 5. 既存実装のパターンをそのままテンプレートとして横展開する
新規アカウント・新規機能は、類似の既存実装をコピーして差分だけ変更する方式が実装速度・品質の両面で最も効率的だった。
- 根拠: Migoron→スクアードX→jake_images（コード構成の横展開）, SCAD Beauty⇔SCAD CHAT（Aboutページフォーマット・アドバイザー制UIの相互横展開）

## 6. 「動的生成→失敗時は静的フォールバック」の二段構え
鮮度が重要なコンテンツ（ニュース等）は都度AI生成が必要だが、AI障害時に無投稿になるリスクがある。静的フォールバックを必ず用意する。
- 根拠: jake_images（実例20本フォールバック）, スクアード（DECODEの段階的フォールバック：個人実データ→セグメント統計→一般論）

## 7. ユーザーが持ち込む数字・通説は鵜呑みにせず一次資料で検証する
「よく聞く数字」「思い込みの通説」はAIが検証役を果たすべき典型パターン。検証を怠らなかったことで誤情報の拡散を未然に防げた。
- 根拠: スクアードX（離婚率統計の誤り訂正）, SCAD Beauty（Google Custom Search API終了情報の事前把握）

## 8. 非技術者との開発は「コードは部分diffでなく全文で受け取り、削除→新規作成で置換」を徹底する
部分diffの貼り付けミス・二重定義は複数プロジェクトで独立に発生した典型事故。全文置換の運用に統一することで再発を防げた。
- 根拠: Migoron（スマホ部分編集での二重定義事故）, スクアード/DECODE（作業スタイルとして明文化）, SCAD Beauty（複数セッション並行編集の混乱）

## 9. AIモデル名は決め打ちせず、`-latest`エイリアスや1箇所の定数に集約する
モデル廃止による404エラーが複数プロジェクトで繰り返し発生したため、エイリアス採用や変更箇所の一元化を標準運用にした。
- 根拠: SCAD Beauty（`-latest`採用）, スクアード/DECODE v2（モデル名を1定数に集約、エラー時は一覧取得）, Migoron（過去のモデル変更対応の教訓）

## 10. 影響範囲のある判断は都度ユーザーに一言確認してから進める
既存アカウントの流用や新規PRのマージなど、後戻りしにくい判断は先に確認を挟むことで手戻りなく合意形成できた。
- 根拠: jake_images（御朱印アカウント流用前の確認）, SCAD Beauty（要件を出し切ってから一括実装方針を確認）

## 11. チャットAIの応答は「段階的開示」にすると体験が向上する
①短い共感・回答→②深掘りの余地があれば一言提案→③ユーザーが望めば見出し限定の詳細フォーマット、という3段階で情報量を制御する。分析レポートを最初から全部出さず、必要な人だけ深掘りできるようにする設計。
- 根拠: SCAD CHAT（3段階レスポンス設計）, スクアード/DECODE v2（「分析レポートを開く」ボタンによる折りたたみ表示も同系統の思想）

## 12. UI崩れは「疑わしい原因を1つ直す」より「絶対に見える場所へ移動」で解決する方が早いことがある
原因の深追いより、レイアウト上確実に表示される位置へ要素を再配置する荒療治が有効な場面がある。
- 根拠: SCAD CHAT（ヘッダー右上ボタンの表示不具合を独立バーへ移動して解決）
