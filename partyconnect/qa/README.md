# バックエンドテスト / アルゴリズム検証

男性10名(M1〜M10)・女性10名(W1〜W10)、計20名でのバックエンド検証一式。
**マッチングの集計結果（誰と誰が成立するか）は、このディレクトリのどのファイルにも書いていない。**
実際に動かして確認すること（`algorithm-test.ts` はデフォルトで結果を表示するが、`--quiet` を付ければ構造検証だけになる）。

## ファイル構成

| ファイル | 内容 |
|---|---|
| `data/profiles.json` | 20名分のプロフィール登録データ |
| `data/likes.json` | 好印象（第一印象）。各3〜8名、重複なし、範囲1〜10 |
| `data/finals.json` | 最終投票。**指定された投票パターンのとおり**（`voteFor`は可読用、`targetNumbers`が実際の送信値） |
| `data/invalid-cases.json` | 異常系3件の仕様書（リクエスト形と期待結果） |
| `algorithm-test.ts` | アルゴリズムだけを検証する単体テスト（サーバー不要・副作用なし） |
| `backend-integration-test.mjs` | 実際にデプロイ済みのEdge Functions/RPCを叩く統合テスト |

## 実データとの対応関係

このアプリの参加者番号は **男女それぞれ1から独立して採番される**（M1〜M10とW1〜W10は別の番号空間）。
そのため `M{n}` → 男性番号n、`W{n}` → 女性番号nとして、変換なしでそのまま対応する。

投票APIは相手を「番号」でしか指定できず、相手のIDや性別を直接指定することはできない
（送信者の性別はセッション側で強制決定され、相手は自動的に異性テーブルから解決される）。

## 1. アルゴリズム単体検証（サーバー不要）

実際にデプロイされているマッチングロジック本体（`supabase/functions/_shared/matching.ts`）を
直接呼び出す。ネットワーク・DBを一切使わないため、繰り返し実行しても安全。

```bash
# 結果を見ずに構造検証だけ行う（二重割当がないか、スコア範囲、ID整合性、seed非依存のペア数）
deno run --allow-read qa/algorithm-test.ts --quiet

# 結果も見る場合
deno run --allow-read qa/algorithm-test.ts
```

指定された投票パターンは、男性2〜8番と女性2〜8番のほぼ全員が女性9・10番／男性9・10番を
第2〜3希望に含めており、「相互指名かつ組数最大化」のロジックが人気者(9番・10番)を
どちらか一方にしか割り当てられない、という競合状態を意図的に作るデータになっている。
アルゴリズムの検証にはちょうどよい負荷になるはず。

## 2. バックエンド統合テスト（実際のAPIを叩く）

### 事前準備（手動・1回だけ）

主催者ログインはメールのマジックリンク認証のため、完全自動化はできない。
以下だけ手動で行う。

1. 主催者コンソールで新規イベントを1件作成する（参加者はまだ発行しない）
2. ブラウザの開発者ツールのコンソールで、ログイン中のアクセストークンを取得する
   ```js
   (await window.__supabase?.auth.getSession() ?? await supabase.auth.getSession()).data.session.access_token
   ```
   ページ内にSupabaseクライアントの参照がない場合は、Application/Storageタブから
   `sb-<project-ref>-auth-token` の中の `access_token` を直接コピーしてもよい。
3. 作成したイベントのURL（`/organizer/<eventId>`）から `eventId` を控える

### 実行

```bash
SUPABASE_URL="https://xxxxx.supabase.co" \
SUPABASE_ANON_KEY="ey..." \
ORGANIZER_ACCESS_TOKEN="ey..." \
EVENT_ID="00000000-0000-0000-0000-000000000000" \
node qa/backend-integration-test.mjs
```

これで実行されるのは:

1. 指定イベントに参加者がいないことを確認（誤って本番イベントを汚さないための安全弁）
2. 男女10枠ずつ発行 → ① 参加者登録（会場QR相当のチェックイン）
3. 20名分のプロフィール登録
4. ② 歓談開始 → ③ 好印象投票（20名分）
5. 異常系 INVALID-1（性別改ざん）・INVALID-3（存在しない番号）をこのタイミングで実行
6. ④ 好印象開示 → ⑤ 最終希望（指定パターンどおり20名分）
7. 異常系 INVALID-2（4人選択）をこのタイミングで実行
8. 進捗が20/20になっていることを確認
9. `RUN_FINALIZE=true` を付けない限り、⑥確定はせず `preview_result` の組数だけ取得して停止する
   （このJSON/READMEに正解を書かない、という指示に合わせた既定動作）

`RUN_FINALIZE=true` を追加すると ⑥確定して結果を配信 まで実行する。**不可逆**なので、
やり直しが必要な場合は毎回新しいイベントを作り直すこと。

### 出力の読み方

各行の `✓` は成功、`✗` は失敗。最後に `失敗 N 件` とまとめて出る。
CIに組み込む場合は終了コード（0=成功 / 1=失敗）で判定できる。

## 3. 異常系（`data/invalid-cases.json`）についての注意

要件どおり3件用意したが、**INVALID-1（同性への投票）だけ、このアプリの実装上エラーにならない**。

このアプリは「送信者の性別」をクライアントの申告からではなくセッション（サーバー側）から
強制的に決定し、投票の相手は常に異性のテーブルからしか解決しない。したがって
「同性の番号を狙って送る」というリクエスト自体を、そもそもクライアント側から
構成できない設計になっている（実際、過去に発生した「同性に★が誤表示される」という
表示バグの反省を踏まえて、投票の集計ロジック自体はもともとID起点で厳密に異性間限定に
なっていたことが判明している）。

そのためINVALID-1は「同性投票が拒否されるテスト」ではなく、
**「クライアントが `gender` フィールドを偽って送っても無視され、同性への投票は成立しない」**
ことを確認する回帰テストとして用意した。むしろこちらの方が
「同性投票はできない」を保証する、より厳密なテストになっている。

INVALID-2（最終希望4人以上）とINVALID-3（存在しない番号99）は、
要件どおりそのまま400エラーを検証するテストになっている。
